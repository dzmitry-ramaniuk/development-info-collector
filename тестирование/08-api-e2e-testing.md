## Область проверки

API-тест обычно вызывает сервис напрямую: он быстрее UI E2E и точнее локализует дефект. E2E идёт через публичную границу и реальные зависимости, доказывая лишь немногие критические journeys.

## HTTP-контракт

Для каждой операции проверяйте:

- method, path, query encoding, обязательные/неизвестные параметры;
- статус и допустимые переходы (`201` + `Location`, `204` без тела, согласованный `4xx`);
- `Content-Type`, `Accept`, charset, cache/conditional headers и correlation ID;
- JSON schema: required/nullable, типы, границы, форматы, enum и дополнительные поля;
- бизнес-инварианты и побочные эффекты в БД/очереди, а не только снимок body;
- пагинацию, сортировку, фильтры и стабильность cursor;
- единый формат ошибки без stack trace и внутренних идентификаторов.

```bash
# Минимальная воспроизводимая проверка публичного HTTP-контракта
response="$(curl -sS -i -H 'Accept: application/json' \
  'http://localhost:8080/orders/42')"
printf '%s' "$response" | head -n 1 | grep -q ' 200 '
printf '%s' "$response" | grep -qi '^Content-Type: application/json'
printf '%s' "$response" | sed -n '/^\r$/,$p' | jq -e \
  '.id == 42 and (.status | type == "string")'
```

Для основного набора применяйте программный HTTP client и JSON Schema validator: shell-пример показывает границы, но плохо масштабируется и не заменяет отчётность.

## Негативные сценарии

Различайте классы ошибок, не ограничиваясь «не 200»:

| Класс | Примеры | Проверка |
|---|---|---|
| Синтаксис | битый JSON, неверный media type/encoding | `400`/`415`, безопасная структурированная ошибка |
| Валидация | отсутствует required, overflow, пустая строка, неизвестный enum | согласованный `4xx`, точный field path, нет side effect |
| Ресурс | неизвестный/чужой ID, удалённая версия | `404` без утечки существования чужого объекта |
| Конкуренция | stale ETag/version, duplicate request | `409`/`412` по контракту, состояние целостно |
| Зависимость | timeout, `429`, частичный отказ | bounded timeout, retry policy, без двойной записи |

Границы проверяют значениями `min-1`, `min`, `max`, `max+1`; property-based/fuzz тесты дополняют, но не заменяют именованные бизнес-сценарии. После любого отказа проверяйте отсутствие нежелательного изменения состояния.

## Идемпотентность

**Идемпотентность** означает одинаковый целевой эффект повторов, а не обязательно одинаковый HTTP-ответ. `PUT` и `DELETE` имеют идемпотентную семантику; для командного `POST` часто вводят `Idempotency-Key`.

Сценарий для `POST /payments`:

1. Отправить один payload с ключом `K`, оборвать/не прочитать ответ.
2. Повторить тот же запрос с `K` последовательно и конкурентно.
3. Убедиться: одна операция/проводка, один business ID, согласованный replay response.
4. Повторить `K` с другим payload: сервер должен отклонить конфликт, а не вернуть старой операции успех.
5. Проверить срок хранения ключа и поведение после его истечения согласно контракту.

> Retry выполняют только при классифицированной временной ошибке, с ограничением попыток/backoff. Автоматический retry неидемпотентной команды без ключа способен удвоить эффект.

## Authentication и authorization

**Authentication** отвечает «кто это?», **authorization** — «разрешено ли этому субъекту это действие над этим объектом?». Матрица должна покрывать роль × действие × объект/tenant × состояние объекта.

- Нет credential; malformed/expired/not-yet-valid token; неверные issuer, audience, signature и algorithm.
- Валидный token без scope/role; read-only субъект пытается изменить данные.
- **BOLA/IDOR:** заменить `orderId` на ID другого пользователя/tenant во всех path, query и body.
- **BFLA:** обычный пользователь вызывает admin endpoint или меняет method/path.
- Mass assignment: передать `role`, `ownerId`, `price` и другие server-controlled поля.
- Revocation/logout, rotation ключей и clock skew проверять согласно модели системы.
- Ошибка не должна раскрывать, существует ли чужой ресурс; логи не должны содержать token/API key.

Позитивный тест одного администратора не доказывает запреты. Для каждого разрешающего правила нужен ближайший запрещающий сценарий; состояние проверяется после отказа.

## E2E-сценарии

Выбирайте journeys по риску: вход → заказ → платёж → подтверждение; восстановление после временного отказа; отмена. Управляйте данными через API/fixtures, применяйте уникальный namespace, ожидайте асинхронность polling с deadline вместо `sleep`, сохраняйте correlation ID и очищайте только свои данные.

Не маскируйте дефекты бесконечными retry. Quarantine допустим с владельцем, причиной и сроком; иначе flaky test перестаёт быть сигналом.

## Таблица выбора

| Нужно узнать | Предпочтительный тест | Почему не более широкий |
|---|---|---|
| Ветка чистой бизнес-логики | Unit/property | Быстрее и детерминированнее |
| Consumer и provider согласны о сообщении | Contract | Не требует совместного окружения |
| Endpoint соблюдает HTTP и пишет в реальную БД | API/component integration | Локализует сервис и инфраструктуру |
| Два реальных сервиса действительно связаны | Integration | Contract не проверяет сеть/конфигурацию |
| Критический путь работает в сборке | Небольшой E2E smoke | Доказывает wiring, но дорог и хрупок |
| SLA под моделью нагрузки | Performance | Функциональный E2E не создаёт workload |
| Запрет доступа/класс уязвимостей | Security | Нужны adversarial inputs и матрица прав |

## Упражнения

1. Для CRUD API составьте матрицу статус × media type × роль и реализуйте три негативных сценария.
2. Напишите конкурентный тест `Idempotency-Key` на 10 одинаковых запросов и проверьте БД/события.
3. Сократите набор из 30 UI E2E до API/component тестов и трёх risk-based journeys.

## Вопросы для самопроверки

1. **Почему проверка только status code недостаточна?**
   Она не проверяет headers, schema, семантику данных и побочные эффекты.
2. **В чём разница между authentication и authorization?**
   Первая устанавливает субъект, вторая разрешает конкретное действие над конкретным ресурсом.
3. **Что доказывает повтор `POST` с idempotency key?**
   Только при проверке хранилища/событий — что повторы одной команды не создали второй бизнес-эффект.
4. **Когда нужен E2E вместо API-теста?**
   Когда риск находится в wiring нескольких систем или пользовательском маршруте, а не внутри одного API.
