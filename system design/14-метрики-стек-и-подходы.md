## Зачем отдельно проектировать метрики

Метрики — это не «добавим потом», а часть архитектуры production-системы. Если заранее не определить, что измерять и как интерпретировать сигнал, то при инциденте команда видит шум вместо причины.

> Практика: сначала фиксируем пользовательские и бизнес-критичные сценарии, затем для каждого сценария определяем SLI и алерты.

## Подходы к метрикам: от ad-hoc к SLI/SLO

Эволюция зрелости обычно выглядит так:

1. **Ad-hoc monitoring** — смотрим CPU/RAM и отдельные графики без явной связи с качеством сервиса.
2. **Service dashboards** — добавляем latency, error rate, traffic по каждому сервису.
3. **SLI/SLO-driven** — определяем измеримые цели качества и error budget.
4. **Product-level observability** — связываем технические метрики с бизнес-воронкой (регистрация, оплата, доставка).

Для backend-систем удобно использовать:
- **RED** (Rate, Errors, Duration) для HTTP/gRPC/API;
- **USE** (Utilization, Saturation, Errors) для инфраструктуры и ресурсов;
- **Golden Signals** как универсальный каркас для дашбордов и on-call.

## Какие метрики собирать в первую очередь

Ниже — минимальный базовый набор для Java-сервиса:

- **Трафик**: RPS, throughput, размер очереди запросов.
- **Ошибки**: 4xx/5xx, исключения по типам, доля timeout.
- **Задержка**: p50/p95/p99 latency по endpoint/операции.
- **Ресурсы JVM**: heap/non-heap, GC pause time, thread states.
- **Интеграции**: latency и error rate внешних API, БД, брокеров.
- **Бизнес-метрики**: успешные заказы, конверсия, время завершения ключевого сценария.

## Elastic Stack для метрик и логов

**Elastic Stack** чаще всего используют, когда нужен единый контур для логов, метрик и поиска по инцидентам.

Базовые компоненты:

- **Elasticsearch** — хранение и поиск временных рядов/документов.
- **Kibana** — дашборды, визуализация и ad-hoc анализ.
- **Beats / Elastic Agent** — сбор телеметрии с хостов/контейнеров.
- **Logstash** (опционально) — обогащение и маршрутизация потока данных.
- **APM Server** — сбор APM-сигналов (трейсы, метрики приложений).

Когда Elastic Stack особенно уместен:

- нужна мощная полнотекстовая аналитика и корреляция «логи + метрики + trace-контекст»;
- уже есть экспертиза команды в Elastic ecosystem;
- важна единая платформа с гибкими запросами и визуализацией.

Ограничения и компромиссы:

- стоимость хранения и масштабирования может быстро расти;
- требуется дисциплина по schema/data lifecycle (индексы, retention, rollover);
- нужна регулярная оптимизация запросов и шардирования.

## Open-source стек наблюдаемости

Если нужен максимально открытый и модульный подход, часто выбирают связку:

- **Prometheus** — сбор и хранение метрик;
- **Alertmanager** — маршрутизация и дедупликация алертов;
- **Grafana** — дашборды и алертинг поверх разных источников;
- **Loki** — централизованные логи; стоимость сравнивайте на своих объёмах и query patterns, а не по универсальному обещанию дешевизны;
- **Tempo** или **Jaeger** — распределённый tracing;
- **OpenTelemetry Collector** — единая точка приёма/преобразования телеметрии.

Плюсы open-source стека:

- открытые интерфейсы и возможность сменить поставщика; формат данных, запросы, dashboards и эксплуатационные процедуры всё равно создают стоимость миграции;
- гибкая компоновка под конкретную нагрузку;
- большой выбор интеграций для Kubernetes и облаков.

Минусы:

- больше операционной ответственности на команду;
- нужно проектировать federation/long-term storage/high availability заранее;
- сложнее обеспечить «из коробки» единый пользовательский опыт, чем в монолитных платформах.

## Java: фреймворки и библиотеки для метрик

Практически полезные инструменты для Java-приложений:

- **Micrometer** — стандарт де-факто для метрик в Spring Boot, единый facade над registry.
- **Spring Boot Actuator** — готовые endpoint-ы health/info/metrics и интеграция с Micrometer.
- **OpenTelemetry Java SDK + javaagent** — трейсинг и метрики с автоинструментированием.
- **Prometheus Java client** — нативная экспозиция метрик в формате Prometheus.
- **Dropwizard Metrics** — проверенная библиотека, часто встречается в legacy/infra-проектах.
- **JMX Exporter** — экспорт JMX/JVM метрик в Prometheus-совместимый формат.

Рекомендации по выбору:

1. Для **Spring Boot** чаще всего: Actuator + Micrometer + OpenTelemetry.
2. Для «чистой» Java без Spring: OpenTelemetry SDK/agent + Prometheus client.
3. Для миграции legacy: постепенно унифицировать метрики через Micrometer bridge/registry и убрать дублирующие счётчики.

## Рекомендуемые архитектурные подходы

- **Единая схема именования метрик**: сервис, операция, результат, окружение.
- **Кардинальность под контролем**: избегайте tag-ов с userId/orderId/requestId.
- **SLO-ориентированные алерты**: меньше alert fatigue, больше сигнала.
- **Runbook рядом с алертом**: у каждого критичного алерта должна быть инструкция действий.
- **Инструментирование по слоям**: edge/API, бизнес-операции, интеграции, инфраструктура.
- **Retention по ценности**: краткосрочные high-resolution данные + долгосрочные агрегаты.

## Практический минимальный план внедрения

1. Выберите 2–3 критичных user journey и зафиксируйте их SLI/SLO.
2. Подключите JVM + HTTP метрики и базовый dashboard RED/USE.
3. Настройте 5–7 ключевых алертов (ошибки, latency, saturation).
4. Добавьте трассировку для внешних интеграций (БД, брокер, внешние API).
5. Введите review метрик в Definition of Done для новых фич.
6. Раз в спринт удаляйте шумные/неполезные алерты и дашборды.

## Сквозной пример: чтение товара, SLI и алерт

### Контракт измерения и инструментирование

Возьмём [CRUD-практикум](../практикумы/01-синхронный-crud-сервис.html). Отдельно определим: availability SLO 99,9% за 30 дней для валидных чтений и latency objective — 95% тех же чтений успешны за 150 мс. Второй показатель считает ошибку плохим событием независимо от её скорости; это не percentile только успешных запросов. Ожидаемые ответы на неизвестный id исключаются по заранее определённой политике, ошибочный `404` по существующему товару исключать нельзя. В production наблюдение на edge включает отказы, которые не дошли до приложения; локальный пример показывает только завершённые операции внутри процесса.

Ниже полный Java-класс с синтетическими измерениями; он не запускает HTTP-сервис и не создаёт искусственные задержки через `sleep`. Для сборки нужны JDK 21, Maven 3.9+ и доступ к Maven Central. Создайте каталог `work/metrics-lab/src/main/java/` и сохраните класс как `MetricsDemo.java`. В Spring Boot используйте согласованные версии BOM вместо независимого переопределения Micrometer.

```java
import io.micrometer.core.instrument.Timer;
import io.micrometer.prometheusmetrics.PrometheusConfig;
import io.micrometer.prometheusmetrics.PrometheusMeterRegistry;
import java.time.Duration;

public class MetricsDemo {
    private static Timer timer(PrometheusMeterRegistry registry, String outcome) {
        return Timer.builder("catalog.read")
            .description("Duration of eligible catalog reads")
            .tags("operation", "get_product", "outcome", outcome)
            .serviceLevelObjectives(Duration.ofMillis(150))
            .publishPercentileHistogram()
            .register(registry);
    }

    public static void main(String[] args) {
        var registry = new PrometheusMeterRegistry(PrometheusConfig.DEFAULT);
        try {
            Timer success = timer(registry, "success");
            Timer error = timer(registry, "error");
            for (int i = 0; i < 980; i++) success.record(Duration.ofMillis(100));
            for (int i = 0; i < 10; i++) success.record(Duration.ofMillis(200));
            for (int i = 0; i < 10; i++) error.record(Duration.ofMillis(50));
            if (success.count() != 990 || error.count() != 10) {
                throw new IllegalStateException("Unexpected fixture counts");
            }
            System.out.print(registry.scrape());
        } finally {
            registry.close();
        }
    }
}
```

Сохраните рядом `work/metrics-lab/pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>
  <groupId>example</groupId>
  <artifactId>metrics-lab</artifactId>
  <version>1.0.0</version>
  <properties>
    <maven.compiler.release>21</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>
  <dependencies>
    <dependency>
      <groupId>io.micrometer</groupId>
      <artifactId>micrometer-registry-prometheus</artifactId>
      <version>1.15.0</version>
    </dependency>
  </dependencies>
  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.13.0</version>
      </plugin>
      <plugin>
        <groupId>org.codehaus.mojo</groupId>
        <artifactId>exec-maven-plugin</artifactId>
        <version>3.5.0</version>
        <configuration><mainClass>MetricsDemo</mainClass></configuration>
      </plugin>
    </plugins>
  </build>
</project>
```

```bash
mvn -q -f work/metrics-lab/pom.xml compile exec:java > work/metrics-lab/metrics.prom
rg 'catalog_read_seconds_(count|bucket)' work/metrics-lab/metrics.prom
```

Файл `metrics.prom` — snapshot fixture, не time series. Однократный запуск не даёт `rate` за пять минут: ниже PromQL применяется к настоящему длительно работающему scrape target. Для fixture проверяйте абсолютные counts и доли напрямую.

В реальном handler измеряйте фактическое время через `Timer.Sample` и записывайте ровно один outcome в конце операции, включая исключение/timeout. Не добавляйте `productId`, raw URL или exception message в labels. Здесь `operation` и `outcome` имеют ограниченное число значений; `instance`/`job` добавляет scrape-конфигурация.

В scrape должны быть `catalog_read_seconds_count`, `_sum` и `_bucket`, в том числе bucket `le="0.15"`. Для fixture сумма count — 1000, success count — 990, success bucket до 150 мс — 980. Если формат представления границы отличается, проверьте exporter версию и реально опубликованный label, затем согласуйте query. Сам факт наличия `/metrics` не проверяет ни buckets, ни полноту наблюдений.

### Агрегация и вычисление SLI

Для постоянно работающего сервиса и scrape-интервала 15 секунд используйте окна с несколькими наблюдениями. Сначала `rate` для каждой counter series, потом суммирование по инстансам: иначе reset одного процесса может исказить расчёт.

```promql
# Availability: успешные операции / все eligible операции.
sum(rate(catalog_read_seconds_count{job="catalog",outcome="success"}[5m]))
/
sum(rate(catalog_read_seconds_count{job="catalog"}[5m]))

# Быстрые успешные / все eligible операции: latency objective 95%.
sum(rate(catalog_read_seconds_bucket{job="catalog",outcome="success",le="0.15"}[5m]))
/
sum(rate(catalog_read_seconds_count{job="catalog"}[5m]))

# Диагностический p95 успешных чтений по всем инстансам.
histogram_quantile(0.95,
  sum by (le) (rate(catalog_read_seconds_bucket{job="catalog",outcome="success"}[5m]))
)
```

Histogram buckets можно агрегировать до вычисления quantile; готовые p95 разных инстансов усреднять нельзя. p95 — диагностический сигнал, SLI выше считает долю событий относительно точного bucket. Fixture соответствует availability `990/1000=99%`, fast-success `980/1000=98%`: availability цель нарушена, latency цель выполнена. Для настоящего 30-дневного SLO нужны данные за соответствующее окно, а не перенос 5-минутного результата на месяц.

При отсутствии трафика отношение не определено: показывайте «нет данных», а не 100% успеха. Отсутствие scrape проверяется отдельным `up`/missing-series сигналом. Длинные незавершённые запросы не попадут в timer до завершения — дополните in-flight/saturation и клиентским наблюдением.

### Burn-rate и сценарии проверки

Для availability SLO 99,9% допустимая error fraction `0.001`. Если error fraction равна `0.01`, budget burn rate `0.01/0.001=10`; при постоянной интенсивности весь 30-дневный бюджет исчерпается примерно за 3 дня. Это оценка при сохранении нагрузки/доли ошибок, а не обещание точного времени.

Быстрый page-кандидат — ошибки >`14.4 × 0.001 = 0.0144` одновременно в окнах 1 час и 5 минут. Пример проверяет длительную проблему и то, что она продолжается; для низкого трафика нужна отдельная политика, а не безусловный page по одному запросу.

```yaml
groups:
  - name: catalog-slo
    rules:
      - alert: CatalogAvailabilityFastBurn
        expr: |
          (
            sum(rate(catalog_read_seconds_count{job="catalog",outcome="error"}[1h]))
            / sum(rate(catalog_read_seconds_count{job="catalog"}[1h])) > 0.0144
          )
          and
          (
            sum(rate(catalog_read_seconds_count{job="catalog",outcome="error"}[5m]))
            / sum(rate(catalog_read_seconds_count{job="catalog"}[5m])) > 0.0144
          )
        labels:
          severity: page
        annotations:
          summary: "Быстро расходуется availability budget каталога"
          description: "Проверь edge errors, saturation DB pool, deploy и зависимые сервисы; затем применяй runbook."
```

В общем окружении ограничьте запросы одним сервисом/окружением или сохраняйте соответствующие labels при агрегации. В production добавьте owner и рабочую ссылку runbook, а также медленный burn-rate, pending-duration и policy для малой нагрузки по результатам эксперимента.

| Сценарий | Ожидаемое доказательство |
|----------|--------------------------|
| Fixture 980 fast success + 10 slow success + 10 errors | Count=1000, availability=99%, fast-success=98%; обе формулы используют один denominator |
| Два инстанса с разным RPS | Суммирование buckets/count до отношения/quantile; результат отличается от среднего двух p95 |
| Перезапуск одного инстанса | `rate` обрабатывает reset; нет искусственного отрицательного throughput |
| 2% errors в обоих окнах, затем восстановление | Burn rate=20, fast-burn условие истинно; после очистки 5-минутного окна условие ложно |
| Нулевой трафик и отдельно пропавший scrape target | Не выводится «100%»; SLI no-data и инфраструктурная недоступность различимы |

Проверка готовности: исходник/версия exporter, raw scrape fixture, запросы, результаты по таблице и журнал тестового алерта. Код в статье — учебная иллюстрация; для реального запуска добавьте scrape target и собственный test harness, не объявляйте алерт проверенным только по чтению YAML.

В этой ревизии выполнены compile/run Java fixture, `promtool check metrics`, `promtool check rules` и `promtool test rules`: availability/fast-success 99%/98%, page при 2% errors и его снятие после восстановления, отсутствие ложного page при нулевом трафике, а также p95 по buckets двух инстансов с разным RPS. Для сравнения чисел с плавающей точкой test harness использует `fuzzy_compare: true`. Это проверка выражений на синтетических рядах; сброс counters, реальный scrape и доставка алерта требуют отдельных интеграционных прогонов.

## Типичные ошибки

- чрезмерная детализация метрик на старте без понятной цели;
- «метрики ради метрик» без связи с SLO и бизнес-риском;
- высокая кардинальность лейблов, которая ломает storage/query;
- отсутствие владельца дашборда и алертов;
- отсутствие тестов наблюдаемости (проверок, что метрики действительно публикуются).
