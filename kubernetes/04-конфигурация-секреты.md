# Конфигурация и секреты в Kubernetes

> **Проверенный baseline:** Kubernetes **1.34** (стабильный minor-релиз). Все встроенные `apiVersion`, манифесты и команды на этой странице сверены с документацией v1.34. Для кластера с `kube-apiserver` 1.34: `kubectl` поддерживается в диапазоне **1.33–1.35**; `kubelet` не может быть новее API server и поддерживается в диапазоне **1.31–1.34**; `kube-controller-manager`, `kube-scheduler` и `cloud-controller-manager` не должны быть новее `kube-apiserver` и могут отставать не более чем на один minor. В HA control plane версии `kube-apiserver` могут различаться не более чем на один minor. Подробнее: [Version Skew Policy](https://v1-34.docs.kubernetes.io/releases/version-skew-policy/).

## ConfigMaps

**ConfigMap** — хранение конфигурационных данных в виде key-value пар.

### Создание ConfigMap

#### Из literal значений:

```bash
kubectl create configmap app-config \
  --from-literal=database_url=postgres://db:5432 \
  --from-literal=cache_enabled=true
```

#### Из файла:

```bash
# app.properties
database_url=postgres://db:5432
cache_enabled=true
log_level=info

kubectl create configmap app-config --from-file=app.properties
```

#### Из директории:

```bash
kubectl create configmap app-config --from-file=./config/
```

#### Из YAML манифеста:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  database_url: "postgres://db:5432"
  cache_enabled: "true"
  log_level: "info"
  app.properties: |
    database_url=postgres://db:5432
    cache_enabled=true
    log_level=info
```

### Использование ConfigMap

#### Как environment variables:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-pod
spec:
  containers:
  - name: app
    image: myapp:1.0
    env:
    # Отдельные ключи
    - name: DATABASE_URL
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: database_url
    # Все ключи из ConfigMap
    envFrom:
    - configMapRef:
        name: app-config
```

#### Как volume:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-pod
spec:
  containers:
  - name: app
    image: myapp:1.0
    volumeMounts:
    - name: config
      mountPath: /etc/config
      readOnly: true
  volumes:
  - name: config
    configMap:
      name: app-config
```

#### Конкретные файлы из ConfigMap:

```yaml
volumes:
- name: config
  configMap:
    name: app-config
    items:
    - key: app.properties
      path: application.properties
```

### Обновление ConfigMap

```bash
# Редактировать
kubectl edit configmap app-config

# Или применить новый манифест
kubectl apply -f configmap.yaml
```

> **Важно**: Поды не перезапускаются автоматически при изменении ConfigMap. Нужно перезапустить поды вручную или использовать Rolling Update deployment.

## Secrets

**Secret** — API-объект для передачи чувствительных данных (паролей, токенов, ключей), но **не зашифрованное хранилище по умолчанию**. `data` — только base64, а не encryption. Защита требует RBAC, шифрования at rest, TLS, audit и ограничения доступа Pod к namespace.

### Типы Secrets

1. **Opaque** (generic) — произвольные key-value данные
2. **kubernetes.io/service-account-token** — legacy long-lived ServiceAccount token; для Pod используйте короткоживущие автоматически ротируемые токены через TokenRequest/projected volume
3. **kubernetes.io/dockerconfigjson** — Docker registry credentials
4. **kubernetes.io/tls** — TLS сертификаты
5. **kubernetes.io/ssh-auth** — SSH ключи
6. **kubernetes.io/basic-auth** — Basic authentication

### Создание Secrets

#### Generic Secret:

```bash
kubectl create secret generic db-secret \
  --from-literal=username=admin \
  --from-literal=password=secretpass123
```

#### Из файлов:

```bash
kubectl create secret generic tls-secret \
  --from-file=tls.crt=server.crt \
  --from-file=tls.key=server.key
```

#### Docker Registry Secret:

```bash
kubectl create secret docker-registry regcred \
  --docker-server=docker.io \
  --docker-username=myuser \
  --docker-password=mypassword \
  --docker-email=myemail@example.com
```

#### TLS Secret:

```bash
kubectl create secret tls tls-secret \
  --cert=path/to/tls.cert \
  --key=path/to/tls.key
```

#### YAML манифест:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  username: YWRtaW4=      # base64 encoded "admin"
  password: c2VjcmV0cGFzcw==  # base64 encoded "secretpass"
```

```bash
# Base64 encoding
echo -n 'admin' | base64
# YWRtaW4=

# Base64 decoding
echo 'YWRtaW4=' | base64 --decode
# admin
```

#### StringData (без base64):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:
  username: admin
  password: secretpass
```

### Использование Secrets

#### Как environment variables:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-pod
spec:
  containers:
  - name: app
    image: myapp:1.0
    env:
    - name: DB_USERNAME
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: username
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: password
```

#### Как volume (более безопасно):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-pod
spec:
  containers:
  - name: app
    image: myapp:1.0
    volumeMounts:
    - name: secret-volume
      mountPath: /etc/secrets
      readOnly: true
  volumes:
  - name: secret-volume
    secret:
      secretName: db-secret
```

Файлы в контейнере:
```
/etc/secrets/username
/etc/secrets/password
```

#### ImagePullSecrets:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: private-app
spec:
  imagePullSecrets:
  - name: regcred
  containers:
  - name: app
    image: private-registry.com/myapp:1.0
```

### Безопасность Secrets

1. Включите [encryption at rest](https://v1-34.docs.kubernetes.io/docs/tasks/administer-cluster/encrypt-data/) для `secrets` в конфигурации API server, храните ключи отдельно и после включения перепишите существующие Secret. Base64 конфиденциальности не даёт.
2. Давайте `get` только нужным ServiceAccount и конкретным Secret. Права `list`/`watch` фактически раскрывают все Secret в scope; право создавать Pod позволяет прочитать Secret, доступные Pod в namespace.
3. Предпочитайте short-lived credentials и внешний secret manager; не коммитьте plaintext или base64 в Git. Монтирование volume уменьшает случайную утечку через environment/debug output, но само по себе не является границей безопасности.
4. Ограничьте доступ к etcd, включите TLS, audit (не логируя значения Secret), ротацию и namespace isolation. На узлах Secret хранится в `tmpfs` только пока нужен Pod.

```yaml
# Фрагмент EncryptionConfiguration для kube-apiserver; храните ключ вне Git.
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  - aescbc:
      keys:
      - name: key1
        secret: <BASE64_32_BYTE_KEY>
  - identity: {} # fallback для чтения ещё не мигрированных данных
```

После настройки выполните контролируемую миграцию: `kubectl get secrets --all-namespaces -o json | kubectl replace -f -`. Сначала проверьте backup etcd и процедуру восстановления; порядок providers влияет на запись и чтение.

### External Secrets Operator

> `external-secrets.io/v1beta1` ниже — **не встроенный API Kubernetes 1.34**, а CRD External Secrets Operator. Установите совместимую версию оператора и проверьте served-версию командой `kubectl get crd externalsecrets.external-secrets.io -o jsonpath='{.status.storedVersions}'`; при обновлении сверяйтесь с migration guide оператора.

Интеграция с внешними Secret managers:

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-secret
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: db-secret
  data:
  - secretKey: username
    remoteRef:
      key: database/credentials
      property: username
```

## Environment Variables

### Типы переменных окружения

#### 1. Статические значения:

```yaml
env:
- name: ENV_TYPE
  value: "production"
- name: PORT
  value: "8080"
```

#### 2. Из ConfigMap:

```yaml
env:
- name: CONFIG_VALUE
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: some-key
```

#### 3. Из Secret:

```yaml
env:
- name: API_KEY
  valueFrom:
    secretKeyRef:
      name: api-secret
      key: api-key
```

#### 4. Field references (Pod metadata):

```yaml
env:
- name: POD_NAME
  valueFrom:
    fieldRef:
      fieldPath: metadata.name
- name: POD_NAMESPACE
  valueFrom:
    fieldRef:
      fieldPath: metadata.namespace
- name: POD_IP
  valueFrom:
    fieldRef:
      fieldPath: status.podIP
- name: NODE_NAME
  valueFrom:
    fieldRef:
      fieldPath: spec.nodeName
```

#### 5. Resource limits:

```yaml
env:
- name: MEMORY_LIMIT
  valueFrom:
    resourceFieldRef:
      containerName: app
      resource: limits.memory
      divisor: 1Mi
```

### EnvFrom — массовый импорт

```yaml
envFrom:
- configMapRef:
    name: app-config
- secretRef:
    name: app-secrets
- prefix: DB_
  configMapRef:
    name: database-config
```

## Volumes

### Типы Volumes

#### 1. emptyDir
Временное хранилище, живёт с подом.

```yaml
volumes:
- name: cache
  emptyDir: {}

# In-memory emptyDir
volumes:
- name: cache
  emptyDir:
    medium: Memory
    sizeLimit: 1Gi
```

#### 2. hostPath
Монтирует директорию с узла (не рекомендуется для production).

```yaml
volumes:
- name: logs
  hostPath:
    path: /var/log/myapp
    type: DirectoryOrCreate
```

#### 3. configMap

```yaml
volumes:
- name: config
  configMap:
    name: app-config
```

#### 4. secret

```yaml
volumes:
- name: secret
  secret:
    secretName: app-secret
```

#### 5. persistentVolumeClaim

```yaml
volumes:
- name: data
  persistentVolumeClaim:
    claimName: mysql-pvc
```

#### 6. projected
Комбинирует несколько источников в один volume.

```yaml
volumes:
- name: all-in-one
  projected:
    sources:
    - secret:
        name: db-secret
    - configMap:
        name: app-config
    - downwardAPI:
        items:
        - path: "labels"
          fieldRef:
            fieldPath: metadata.labels
```

## Persistent Volumes

### PersistentVolume (PV)

**PV** — физическое хранилище в кластере.

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-example
spec:
  capacity:
    storage: 10Gi
  volumeMode: Filesystem
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: fast
  hostPath:
    path: /mnt/data
```

**Access Modes:**
- **ReadWriteOnce (RWO)** — один узел, read-write
- **ReadOnlyMany (ROX)** — множество узлов, read-only
- **ReadWriteMany (RWX)** — множество узлов, read-write
- **ReadWriteOncePod (RWOP)** — один под, read-write (K8s 1.22+)

**Reclaim Policy:**

| Policy | Что происходит после удаления PVC | Когда выбирать |
|---|---|---|
| **Retain** | PV переходит в `Released`; storage asset и данные остаются, повторное использование требует ручной очистки и подготовки | Критичные данные и ручной recovery workflow |
| **Delete** | Для динамически созданного volume provisioner удаляет PV и backing storage согласно возможностям CSI/провайдера | Временные данные или автоматизированный lifecycle с проверенными backup |
| **Recycle** | **Legacy/deprecated:** примитивный `rm -rf` и возврат volume в пул; dynamic provisioning должен использоваться вместо него | Не использовать в новых конфигурациях |

Reclaim policy принадлежит PV (и задаётся StorageClass для динамического provisioning). Она срабатывает после удаления claim, не заменяет backup и не гарантирует secure erase. До удаления PVC проверьте policy командой `kubectl get pv -o custom-columns=NAME:.metadata.name,CLAIM:.spec.claimRef.name,POLICY:.spec.persistentVolumeReclaimPolicy`.

### PersistentVolumeClaim (PVC)

**PVC** — запрос на хранилище.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: fast
  selector:
    matchLabels:
      type: database
```

### Использование PVC в Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mysql
spec:
  containers:
  - name: mysql
    image: mysql:8.0
    volumeMounts:
    - name: data
      mountPath: /var/lib/mysql
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: mysql-pvc
```

### Volume Expansion

```yaml
# Изменить размер PVC
spec:
  resources:
    requests:
      storage: 20Gi  # Было 10Gi
```

```bash
# Проверить поддержку expansion
kubectl get storageclass fast -o yaml | grep allowVolumeExpansion
```

## Storage Classes

**StorageClass** — автоматическое создание PV (Dynamic Provisioning).

### Примеры StorageClass

#### AWS EBS:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iopsPerGB: "10"
  encrypted: "true"
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
reclaimPolicy: Delete
```

#### GCE PD:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: pd.csi.storage.gke.io
parameters:
  type: pd-ssd
  replication-type: regional-pd
```

#### Local Storage:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-storage
provisioner: kubernetes.io/no-provisioner
volumeBindingMode: WaitForFirstConsumer
```

### Default StorageClass

```yaml
metadata:
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
```

```bash
# Установить default StorageClass
kubectl patch storageclass fast-ssd -p '{"metadata": {"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
```

### Volume Binding Modes

**Immediate** — PV создаётся сразу при создании PVC

**WaitForFirstConsumer** — PV создаётся при создании первого пода (лучше для topology constraints)

## Pod Security Admission

Встроенный **Pod Security Admission (PSA)** в 1.34 применяет [Pod Security Standards](https://v1-34.docs.kubernetes.io/docs/concepts/security/pod-security-standards/) на уровне namespace в режимах `enforce`, `audit` и `warn`. Начинайте с `warn`/`audit`, исправляйте workload и затем включайте `enforce`; версию стандарта фиксируйте, чтобы обновление control plane не меняло требования неожиданно.

```bash
kubectl label --overwrite namespace payments \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=v1.34 \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/audit-version=v1.34 \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/warn-version=v1.34
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: restricted-example
spec:
  automountServiceAccountToken: false
  securityContext:
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: nginx:1.27
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]
      runAsNonRoot: true
    resources:
      requests:
        cpu: 50m
        memory: 32Mi
      limits:
        memory: 64Mi
```

**Legacy:** PodSecurityPolicy (`policy/v1beta1`) deprecated в 1.21 и удалена в 1.25. Не добавляйте PSP в манифесты 1.34; используйте PSA, а для правил вне Pod Security Standards — валидирующий admission webhook/policy engine. PSA валидирует Pod security fields, но не заменяет RBAC, NetworkPolicy, image policy или runtime isolation.

## Best Practices

### ConfigMaps и Secrets

1. **Разделение по окружениям**
```bash
config-dev
config-staging
config-production
```

2. **Версионирование**
```yaml
metadata:
  name: app-config-v2
```

3. **Используйте immutable ConfigMaps/Secrets** (K8s 1.21+)
```yaml
immutable: true
```

4. **Избегайте больших ConfigMaps**
   - Лимит: 1 MB
   - Для больших файлов используйте volumes

### Secrets Security

1. **RBAC ограничения**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: secret-reader
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get"]
  resourceNames: ["specific-secret"]
```

2. **Audit logging**
```yaml
# Аудит доступа к secrets
audit.k8s.io/v1
```

3. **Используйте Sealed Secrets**
```bash
# Шифрование секретов для Git
kubeseal -o yaml < secret.yaml > sealed-secret.yaml
```

### Storage

1. **Используйте PVC вместо PV напрямую**

2. **Backup Persistent Volumes**
```bash
# Velero для backup
velero backup create my-backup --include-resources pvc,pv
```

3. **Мониторинг использования**
```bash
kubectl top pods
kubectl describe pvc
```

4. **Используйте volumeMode правильно**
   - **Filesystem** — для обычных приложений
   - **Block** — для БД с прямым доступом к устройству

## Вопросы для самопроверки

1. **В чём разница между ConfigMap и Secret?**
   - ConfigMap для обычной конфигурации, Secret для чувствительных данных (base64, encryption at rest)

2. **Почему volumes предпочтительнее env для Secrets?**
   - Env variables могут попасть в логи, volumes более безопасны

3. **Что такое Dynamic Provisioning?**
   - Автоматическое создание PV через StorageClass при создании PVC

4. **Какие Access Modes существуют?**
   - RWO (ReadWriteOnce), ROX (ReadOnlyMany), RWX (ReadWriteMany), RWOP (ReadWriteOncePod)

5. **Зачем нужен WaitForFirstConsumer binding mode?**
   - Для учёта topology constraints при создании volume
