## Актуальность материала

- **Дата проверки исправлений:** 2026-10-15: namespaced RBAC и единицы PromQL. Остальная редакция — 2026-08-04; её повторная сверка не заявляется.
- **Целевые версии:** встроенные API Kubernetes 1.34; PromQL Prometheus 3.x. Версии UI, Helm charts, collectors/operators задаются отдельно.
- **Статус примеров:** исправленные RBAC/PromQL — `current` по документации, запуск кластера не заявляется. Остальные сторонние install/config snippets — `template`, требуют проверки выбранных версий; Kubernetes baseline не подтверждает их совместимость.

## Мониторинг кластера

### Metrics Server

**Metrics Server** — базовый компонент для сбора метрик ресурсов.

#### Установка:

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```

#### Использование:

```bash
# Метрики узлов
kubectl top nodes

# Метрики подов
kubectl top pods

# Метрики в конкретном namespace
kubectl top pods -n kube-system

# Сортировка по CPU
kubectl top pods --sort-by=cpu

# Сортировка по памяти
kubectl top pods --sort-by=memory
```

### Kubernetes Dashboard

Dashboard использует Kubernetes RBAC. Для уже установленного и совместимого с вашим кластером UI выдайте отдельному ServiceAccount только чтение ресурсов приложения в **одном namespace**. Установку/версию UI выбирают отдельно; старый manifest v2.7.0 не является baseline для Kubernetes 1.34. Полный административный доступ для просмотра метрик не требуется.

Сохраните как `dashboard-reader.yaml`:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: observability-lab
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: dashboard-reader
  namespace: observability-lab
automountServiceAccountToken: false
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: dashboard-reader
  namespace: observability-lab
rules:
  - apiGroups: [""]
    resources: [pods, services, events]
    verbs: [get, list, watch]
  - apiGroups: [apps]
    resources: [deployments, replicasets, statefulsets, daemonsets]
    verbs: [get, list, watch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dashboard-reader
  namespace: observability-lab
subjects:
  - kind: ServiceAccount
    name: dashboard-reader
    namespace: observability-lab
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: dashboard-reader
```

```bash
kubectl apply -f dashboard-reader.yaml
# Оператору проверки нужны impersonation permissions для --as.
kubectl auth can-i get pods -n observability-lab --as=system:serviceaccount:observability-lab:dashboard-reader
# yes
kubectl auth can-i get secrets -n observability-lab --as=system:serviceaccount:observability-lab:dashboard-reader
# no
kubectl auth can-i create deployments.apps -n observability-lab --as=system:serviceaccount:observability-lab:dashboard-reader
# no
kubectl auth can-i get pods -n kube-system --as=system:serviceaccount:observability-lab:dashboard-reader
# no
kubectl -n observability-lab create token dashboard-reader --duration=10m
```

Последняя команда выдаёт bearer credential: не помещайте его в Git/logs. API server может изменить фактический срок; после опыта удалите binding/SA командой `kubectl delete -f dashboard-reader.yaml`. UI открывайте через предусмотренный его версией локальный port-forward. В UI выбирайте `observability-lab`; запреты на другие namespaces, Secrets, logs и cluster-scoped данные ожидаемы. Чтение Pods раскрывает их spec, поэтому не храните пароли в обычных `env.value`. Границы прав описаны в [RBAC](06-безопасность-и-политики.html#serviceaccount-и-rbac).

### Prometheus

**Prometheus** — система мониторинга и alerting.

#### Установка через Helm:

```bash

  --namespace monitoring \
  --create-namespace
```

#### Prometheus Operator:

```bash

  --namespace monitoring \
  --create-namespace
```

#### ServiceMonitor

**ServiceMonitor** — декларативная конфигурация для scraping метрик.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: app-metrics
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
    interval: 30s
    path: /metrics
```

#### PodMonitor

Для мониторинга подов напрямую.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: app-pods
spec:
  selector:
    matchLabels:
      app: myapp
  podMetricsEndpoints:
  - port: metrics
    interval: 30s
```

#### Prometheus Queries (PromQL)

```promql
# CPU usage
rate(container_cpu_usage_seconds_total[5m])

# Memory usage
container_memory_usage_bytes

# Request rate
rate(http_requests_total[5m])

# Доля 5xx по сервису (0..1); при отсутствии трафика процент не определён
sum by (namespace, service) (rate(http_requests_total{status=~"5.."}[5m]))
/
sum by (namespace, service) (rate(http_requests_total[5m]))

# P95 latency
histogram_quantile(0.95, sum by (namespace, service, le) (rate(http_request_duration_seconds_bucket[5m])))

# Pod restarts
kube_pod_container_status_restarts_total

# Available replicas
kube_deployment_status_replicas_available
```

#### Application Metrics

**Пример с Go:**
```go
import (
    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
    httpRequestsTotal = prometheus.NewCounterVec(
        prometheus.CounterOpts{
            Name: "http_requests_total",
            Help: "Total HTTP requests",
        },
        []string{"method", "endpoint", "status"},
    )
)

func init() {
    prometheus.MustRegister(httpRequestsTotal)
}

func handler(w http.ResponseWriter, r *http.Request) {
    httpRequestsTotal.WithLabelValues(r.Method, "/api/users/{id}", "200").Inc()
}

func main() {
    http.Handle("/metrics", promhttp.Handler())
    http.ListenAndServe(":8080", nil)
}
```

## Логирование приложений

### Стандартный подход

**Логи в stdout/stderr** — стандарт для контейнеров.

```bash
# Просмотр логов
kubectl logs pod-name

# Follow logs
kubectl logs -f pod-name

# Логи конкретного контейнера
kubectl logs pod-name -c container-name

# Последние N строк
kubectl logs --tail=100 pod-name

# Логи за период
kubectl logs --since=1h pod-name

# Логи предыдущего контейнера (после рестарта)
kubectl logs -p pod-name
```

### Distributed Tracing Example

```python
# Python с OpenTelemetry
from opentelemetry import trace
from opentelemetry.exporter.jaeger.thrift import JaegerExporter
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

tracer_provider = TracerProvider()
jaeger_exporter = JaegerExporter(
    agent_host_name="jaeger-agent",
    agent_port=6831,
)
tracer_provider.add_span_processor(BatchSpanProcessor(jaeger_exporter))
trace.set_tracer_provider(tracer_provider)

tracer = trace.get_tracer(__name__)

@app.route('/api/user')
def get_user():
    with tracer.start_as_current_span("get_user"):
        # Your code here
        return {"user": "john"}
```

## Alerting

### Prometheus Alertmanager

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: app-alerts
  namespace: monitoring
spec:
  groups:
  - name: app
    interval: 30s
    rules:
    - alert: HighErrorRate
      expr: |
        (
          sum by (namespace, service) (rate(http_requests_total{status=~"5.."}[5m]))
          /
          sum by (namespace, service) (rate(http_requests_total[5m]))
        ) > 0.05
        and on (namespace, service)
        sum by (namespace, service) (rate(http_requests_total[5m])) >= 1
      for: 5m
      labels:
        severity: critical
      annotations:
        summary: "High error rate detected"
        description: 'Доля 5xx {{ printf "%.3f" $value }} у {{ $labels.namespace }}/{{ $labels.service }}'

    - alert: PodCrashLooping
      expr: increase(kube_pod_container_status_restarts_total[15m]) >= 3
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Pod is crash looping"
        description: "Pod {{ $labels.pod }} is restarting frequently"

    - alert: HighMemoryUsage
      expr: |
        100 * max by (namespace, pod, container) (
          container_memory_working_set_bytes{container!="",container!="POD",image!=""}
        )
        /
        (max by (namespace, pod, container) (
          container_spec_memory_limit_bytes{container!="",container!="POD"}
        ) > 0) > 90
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "High memory usage"
        description: 'Container {{ $labels.container }} using {{ printf "%.1f" $value }}% memory'
```

В этом контракте `http_requests_total` имеет scrape labels `namespace` и `service` на каждой series. Порог 0.05 означает **5%**, а минимум 1 request/s — выбранную учебную защиту от малого sample size (около 300 запросов за окно 5m). При нулевом трафике HighErrorRate не срабатывает: доступность и отсутствие telemetry проверяют отдельными alerts. `rate` возвращает события/сек; деление на все запросы превращает его в долю. Для memory сначала исключены нулевые лимиты и инфраструктурные series, результат выражен в процентах. `increase >= 3` — эвристика повторных рестартов, не доказательство причины CrashLoopBackOff.

[Исполняемые правила и тесты](../examples/infra/03-observability/README.html) проверяют низкую/высокую нагрузку с 1% и 10% ошибок, отсутствие трафика и нулевой memory limit. `promtool` получает обычный rule file без Kubernetes CRD; для Prometheus Operator оберните его `groups` в `PrometheusRule.spec` и согласуйте labels с `ruleSelector` установленного release.

## Best Practices

### Логирование

1. **Используйте структурированные логи** (JSON)
2. **Логируйте в stdout/stderr**, не в файлы
3. **Добавляйте контекст**: request ID, user ID, trace ID
4. **Уровни логирования**: DEBUG, INFO, WARN, ERROR
5. **Ротация логов** на уровне node

### Мониторинг

1. **Golden Signals**:
   - **Latency** — время ответа
   - **Traffic** — количество запросов
   - **Errors** — процент ошибок
   - **Saturation** — использование ресурсов

2. **USE Method** (для ресурсов):
   - **Utilization** — процент использования
   - **Saturation** — очередь/перегрузка
   - **Errors** — количество ошибок

3. **RED Method** (для сервисов):
   - **Rate** — запросы в секунду
   - **Errors** — процент ошибок
   - **Duration** — время ответа

### Alerting

1. **Алерты на симптомы**, не на причины
2. **Actionable alerts** — каждый алерт требует действия
3. **Правильная severity**: critical, warning, info
4. **Избегайте alert fatigue** — не слишком много алертов
5. **Документируйте runbooks** для каждого алерта

### Resource Limits

```yaml
resources:
  requests:
    memory: "256Mi"
    cpu: "100m"
  limits:
    memory: "512Mi"
    cpu: "500m"
```

## Вопросы для самопроверки

1. **Что такое Metrics Server и зачем он нужен?**
   - Компонент для сбора метрик ресурсов (CPU, память), используется для HPA и kubectl top

2. **В чём разница между EFK и ELK стеками?**
   - Fluentd vs Filebeat как log shippers; оба используют Elasticsearch + Kibana

3. **Что такое Golden Signals?**
   - Latency, Traffic, Errors, Saturation — ключевые метрики для SRE

4. **Зачем нужен distributed tracing?**
   - Для отслеживания запросов через микросервисы, выявления bottlenecks

5. **Что такое ServiceMonitor в Prometheus?**
