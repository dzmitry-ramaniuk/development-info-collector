## Актуальность материала

- **Дата проверки:** 2026-08-04
- **Целевая версия или диапазон:** Kubernetes 1.34 (baseline раздела); Helm/Kustomize/GitOps контроллеры версионируются отдельно
- **Статус манифестов:** встроенные `apps/v1` — `current`; Helm templates, Kustomize overlays и GitOps CRD — `current` только для зафиксированных версий соответствующих инструментов
- **Первичные источники:** [Deployments](https://v1-34.docs.kubernetes.io/docs/concepts/workloads/controllers/deployment/); [Kustomize](https://v1-34.docs.kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/); [Helm Documentation](https://helm.sh/docs/); [OpenGitOps Principles](https://opengitops.dev/)

## Supply chain и CI/CD

Безопасный pipeline: commit → tests/SAST → reproducible image → SBOM/signature → immutable registry digest → render/validate policies → deploy в pre-production → progressive production rollout → verification. Не передавайте cluster-admin CI runner: предпочтителен pull-based GitOps controller с namespace-scoped правами. Разделяйте application repo, deployment configuration и secrets; promotion меняет digest, а не пересобирает image.

Минимальные gates: unit/integration tests, manifest schema validation, policy-as-code, vulnerability policy с SLA, smoke test, SLO/error-budget check и ручное подтверждение для рискованных production changes. Credentials делайте short-lived через workload identity/OIDC.

## Helm, Kustomize и GitOps

| Инструмент/подход | Когда удобен | Риски и дисциплина |
|---|---|---|
| Helm | Переиспользуемый пакет, dependencies, параметризация и release history | Сложные templates, values drift; фиксируйте chart/app versions и проверяйте rendered YAML |
| Kustomize | Небольшие overlays поверх читаемой YAML base без шаблонного языка | Overlays разрастаются; фиксируйте remote refs и не дублируйте patches |
| GitOps | Git — desired state, pull/reconciliation, audit и drift correction | Controller/CRD — дополнительный компонент; продумайте secrets, promotion и emergency process |

Helm и Kustomize — способы собрать манифесты, GitOps — operating model; их можно сочетать. В CI всегда сохраняйте `helm template`/`kubectl kustomize` artifact, проверяйте API Kubernetes 1.34 и CRD до custom resources. GitOps reconciler должен игнорировать только действительно controller-owned динамические поля, а не весь drift.

```yaml
# kustomization.yaml — статус current для встроенного Kustomize в kubectl 1.34
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources: [../../base]
images:
  - name: registry.example.com/shop/api
    newName: registry.example.com/shop/api
    newTag: sha256-0123456789abcdef
patches:
  - path: production-resources.yaml
```

В реальном registry digest указывают в формате `image@sha256:<64 hex>`; пример сокращён для читаемости и не применяется как есть.

## Стратегии rollout

**Rolling update** постепенно заменяет Pods. `maxUnavailable` контролирует capacity loss, `maxSurge` — временный запас. Это стандартный компромисс при backward-compatible версии.

**Canary** направляет малую долю трафика/пользователей на новую версию и повышает её ступенями при здоровых SLO. Kubernetes Deployment сам не обеспечивает точный weighted routing: нужен отдельный Deployment и ingress/service mesh/progressive-delivery controller.

**Blue-green** держит полные old/new environments и переключает Service/router. Rollback быстр, но удваивается capacity, а миграции данных всё равно должны быть совместимы.

| Стратегия | Стоимость | Контроль риска | Типичный rollback |
|---|---|---|---|
| Rolling | Низкая/средняя | Probes и темп замены | `rollout undo`/Git revert |
| Canary | Средняя | Метрики по версии и ступени трафика | Трафик на stable, затем scale down canary |
| Blue-green | Высокая | Проверка green до switch | Вернуть selector/route на blue |

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: {name: api, namespace: shop}
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate: {maxUnavailable: 0, maxSurge: 1}
  minReadySeconds: 20
  progressDeadlineSeconds: 600
  selector: {matchLabels: {app: api}}
  template:
    metadata: {labels: {app: api}}
    spec:
      containers:
        - name: api
          image: registry.example.com/shop/api@sha256:REPLACE_WITH_64_HEX_DIGEST
          ports: [{containerPort: 8080}]
          readinessProbe:
            httpGet: {path: /health/ready, port: 8080}
```

Placeholder digest делает пример учебным: перед apply CI обязан заменить его валидным проверенным digest. Статус API — `current`, статус значения image — `template`.

## Безопасный rollback

Rollback — заранее протестированная операция, а не импровизация:

1. Определите автоматические abort criteria: error rate, latency, saturation и business KPI с minimum sample/window.
2. Храните immutable image digest, rendered manifests, config/schema version и provenance каждого release.
3. Делайте БД-изменения **expand/contract**: сначала backward-compatible schema, затем новый код, потом удаление старого. Rollback бинарника не откатит destructive migration.
4. Сначала остановите promotion/автосинхронизацию контролируемым способом, затем revert Git commit (GitOps) или выполните `helm rollback <release> <revision> --wait --atomic` по runbook. Не оставляйте ручной drift.
5. Проверяйте readiness, smoke tests, SLO и события; документируйте incident. Не удаляйте старую ReplicaSet/blue environment до истечения observation window.

`helm --atomic` откатывает неуспешный upgrade Helm release, но не отменяет внешние side effects, Jobs и необратимые миграции. `kubectl rollout undo` зависит от сохранённой Deployment revision и также не откатывает данные/config вне шаблона.

## Production checklist

- Version/digest зафиксированы; `latest` запрещён; image подписан и просканирован.
- Requests, probes, PDB и topology spread соответствуют стратегии.
- Манифесты dry-run/schema/policy-tested на Kubernetes 1.34.
- Canary метрики различают stable/canary, rollback измерен на game day.
- GitOps emergency change возвращается в Git; audit trail не теряется.

## Вопросы для самопроверки

1. **Заменяет ли GitOps Helm?** Нет: GitOps управляет reconciliation, Helm может рендерить/package manifests.
2. **Когда blue-green лучше rolling?** Когда нужен атомарный traffic switch и доступен двойной capacity.
3. **Почему rollback приложения может не помочь?** Schema и внешние side effects могли стать несовместимыми.
4. **Что делает canary безопасным?** Малый blast radius, ступени promotion и автоматические критерии abort.
