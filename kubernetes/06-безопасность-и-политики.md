## Модель защиты

Защита строится слоями: аутентификация субъекта → авторизация запроса → admission-политики → изоляция workload и сети → защита данных и аудит. Namespace — граница организации и части политик, но не полноценная security boundary. Не запускайте контейнеры privileged/root без обоснования, закрепляйте digest образа и отделяйте права CI/CD от runtime identity.

## ServiceAccount и RBAC

**ServiceAccount (SA)** — namespaced identity для Pod и automation. Если SA не указан, используется `default`; токен не следует монтировать процессу, которому API не нужен (`automountServiceAccountToken: false`). Современные projected tokens короткоживущие и ротируются kubelet — не создавайте legacy Secret-токены вручную.

**RBAC** разрешает действия по принципу additive permissions: `Role` действует в namespace, `ClusterRole` — для cluster-scoped ресурсов или повторного использования; `RoleBinding` выдаёт права в одном namespace, `ClusterRoleBinding` — во всём кластере. Явного `deny` нет. Избегайте `cluster-admin`, wildcard и прав изменять RBAC/Secrets/Pods без необходимости: создание Pod фактически позволяет исполнять код с его SA.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: inventory-reader
  namespace: shop
automountServiceAccountToken: true
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: inventory-reader
  namespace: shop
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["inventory-settings"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: inventory-reader
  namespace: shop
subjects:
  - kind: ServiceAccount
    name: inventory-reader
    namespace: shop
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: inventory-reader
```

Проверяйте фактическое решение: `kubectl auth can-i get configmap/inventory-settings --as=system:serviceaccount:shop:inventory-reader -n shop`. Периодически ищите неиспользуемые bindings и разделяйте deployer, operator и application identities.

## NetworkPolicy

**NetworkPolicy** фильтрует L3/L4 трафик для выбранных Pods, только если CNI реализует этот API. Политики складываются аддитивно: соединение разрешено, когда egress источника и ingress назначения разрешают его. Начните с default deny, затем явно откройте DNS, ingress от нужного приложения и egress к конкретным зависимостям.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: shop
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-inventory
  namespace: shop
spec:
  podSelector:
    matchLabels: {app: inventory}
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - podSelector:
            matchLabels: {app: gateway}
      ports:
        - {protocol: TCP, port: 8080}
  egress:
    - to:
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: kube-system}
      ports:
        - {protocol: UDP, port: 53}
        - {protocol: TCP, port: 53}
```

Пример DNS зависит от labels namespace и размещения DNS Pods: проверьте CNI, dual-stack, NodeLocal DNS и реальные endpoints. NetworkPolicy не заменяет mTLS, L7 authorization или firewall облака.

## Pod Security Standards

**Pod Security Standards (PSS)** задают три профиля: `privileged` (без ограничений), `baseline` (запрещает известные опасные настройки) и `restricted` (жёсткий least privilege). Встроенный **Pod Security Admission** применяет их namespace labels в режимах `enforce`, `audit`, `warn`; сначала включайте warn/audit, исправляйте нарушения, затем enforce. Закрепляйте minor-версию политики, чтобы upgrade не менял требования неожиданно.

```bash
kubectl label namespace shop \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=v1.34 \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted
```

Для restricted workload обычно задают `runAsNonRoot`, seccomp `RuntimeDefault`, drop всех capabilities и запрещают privilege escalation. PSS не проверяет registry, подпись образа, ресурсы или business-specific правила — это задача policy engine.

## Шифрование Secrets

Base64 в Secret — кодирование, не шифрование. Включите encryption at rest в `kube-apiserver` через `EncryptionConfiguration`; для production предпочтителен KMS provider v2 с внешним KMS/HSM, ротацией ключей и аудитом. После смены конфигурации перепишите существующие Secrets, иначе старые записи останутся с прежним provider/key. Делайте backup encryption config отдельно от etcd backup и ограничивайте доступ к обоим.

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources: [secrets]
    providers:
      - kms:
          apiVersion: v2
          name: platform-kms
          endpoint: unix:///var/run/kmsplugin/socket.sock
      - identity: {}
```

`identity` в конце позволяет читать незашифрованные старые данные во время миграции; после переписывания и проверки удалите fallback согласно runbook поставщика. Дополнительно используйте external secret manager, не храните plaintext в Git и ограничивайте `get/list/watch secrets`.

## Policy engines

Admission policies дополняют PSS. Встроенный `ValidatingAdmissionPolicy` (`admissionregistration.k8s.io/v1`, CEL) удобен без дополнительного controller. **Kyverno** предлагает Kubernetes-подобные YAML policies, mutation/generation и image verification; **OPA Gatekeeper** — Rego и constraint templates. Их CRD-версии не гарантируются Kubernetes baseline: фиксируйте версию chart/operator, тестируйте upgrade и определяйте `failurePolicy` осознанно.

| Подход | Сильная сторона | Компромисс |
|---|---|---|
| ValidatingAdmissionPolicy | Встроенный CEL, меньше компонентов | В основном validation, возможности зависят от API |
| Kyverno | Знакомый YAML, mutation/generation | Дополнительный controller и CRD |
| Gatekeeper | Выразительный Rego, зрелая библиотека | Более высокий порог и дополнительный failure mode |

Начинайте с audit, покрывайте policy тестами, исключения делайте узкими и временными. Для критической защиты решите, должен ли недоступный webhook блокировать изменения (`Fail`) или сохранять availability (`Ignore`).

## Практический checklist

1. Отдельный SA на workload, токен только при необходимости, least-privilege RBAC.
2. PSS `restricted` и default-deny network policy по умолчанию.
3. Secrets зашифрованы at rest, ключи и backups ротируются и проверяются restore-тестом.
4. Audit logs и алерты на RBAC/admission/Secret access включены.
5. Policy exceptions имеют owner, причину и срок удаления.

## Вопросы для самопроверки

1. **Чем RoleBinding отличается от ClusterRoleBinding?** Первый выдаёт права только в namespace binding, второй — cluster-wide.
2. **Почему default-deny может сломать приложение?** Нужно явно разрешить DNS и все необходимые ingress/egress зависимости.
3. **Заменяет ли PSS policy engine?** Нет: PSS покрывает безопасность Pod, но не организационные правила и supply chain.
4. **Почему недостаточно Secret в etcd?** Без encryption provider содержимое доступно обладателю backup/диска etcd после base64-декодирования.
