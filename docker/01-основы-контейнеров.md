## Контейнерная модель

**Image (образ)** — неизменяемый шаблон: манифест, конфигурация и адресуемые по содержимому слои файловой системы. **Container (контейнер)** — конкретный экземпляр образа: изолированный процесс с runtime-конфигурацией и тонким writable layer. Один образ можно запустить много раз; удаление контейнера не удаляет образ, а данные writable layer обычно исчезают вместе с контейнером.

| Свойство | Image | Container |
|---|---|---|
| Состояние | immutable-шаблон | запущенный или остановленный экземпляр |
| Файловая система | read-only layers | слои образа + writable layer |
| Идентичность | tag и/или digest | имя/ID, PID, сеть, mounts |
| Назначение | доставка | выполнение |

В отличие от VM контейнер не несёт отдельное ядро гостевой ОС: процесс использует ядро host. Поэтому старт и упаковка легче, но граница изоляции иная; контейнер нельзя считать security-сандбоксом автоматически.

## Namespaces и cgroups

Linux **namespaces** меняют то, *что процесс видит*: PID изолирует дерево процессов, mount — точки монтирования, network — интерфейсы/routes, UTS — hostname, IPC — IPC-объекты, user — отображение UID/GID. Процесс внутри может видеть себя PID 1, хотя на host у него другой PID.

**cgroups** управляют тем, *сколько ресурсов процесс получает и как учитывается потребление*: CPU quota/weight, memory limit, PIDs и I/O. Namespace без cgroup скрывает соседей, но не препятствует исчерпанию RAM; cgroup без namespace ограничивает ресурс, но не создаёт отдельное представление системы. Docker связывает эти механизмы с capabilities, seccomp и LSM, но ни один слой сам по себе не равен полной изоляции VM.

```bash
docker run --rm --name demo --memory=256m --cpus=0.5 --pids-limit=100 \
  alpine:3.22 sh -c 'echo "PID=$$ host=$(hostname)"; cat /proc/self/cgroup; sleep 30'
docker stats --no-stream demo
docker rm -f demo
```

## OCI image и registry

**OCI** стандартизует format образа, runtime bundle и distribution API. **Registry** хранит blobs и manifests; repository группирует варианты образа, tag — изменяемый указатель (`app:1.2`), digest — неизменяемый content address (`app@sha256:…`).

Типичный поток: build создаёт layers/config → push загружает отсутствующие blobs и manifest → registry проверяет доступ → pull выбирает manifest под платформу → runtime распаковывает snapshot и запускает процесс. Registry не является запущенным контейнером.

```bash
docker pull alpine:3.22
docker image inspect alpine:3.22 --format '{{json .RepoDigests}}'
docker run --rm alpine:3.22 cat /etc/os-release
```

## Практика

Сравните PID и filesystem:

```bash
docker run -d --name web nginx:1.29-alpine
docker exec web sh -c 'ps; echo changed >/tmp/demo'
docker diff web
docker rm -f web
```

`docker diff` показывает изменения writable layer. Нужные после пересоздания данные следует вынести в volume или внешнее хранилище.

## Проблемы и советы

- Не храните состояние только в writable layer.
- Не путайте `EXPOSE` (метаданные) и `-p` (публикация host port).
- Не используйте плавающий `latest` для воспроизводимого deploy.
- Помните: root в контейнере без user namespace часто соответствует root на host; запускайте workload непривилегированно.

## Практические упражнения

1. Запустите два контейнера из одного image и сравните IDs, PID и изменения `/tmp`.
2. Установите memory limit и наблюдайте `docker stats`.
3. Получите digest образа и объясните отличие от tag.

## Вопросы для самопроверки

1. **Почему image и container — не синонимы?**  
   *Ответ:* Image — неизменяемый шаблон, container — runtime-экземпляр с процессами и writable state.
2. **Что решают namespaces и cgroups?**  
   *Ответ:* Первые изолируют представление ресурсов, вторые учитывают и ограничивают их потребление.
3. **Зачем digest, если есть tag?**  
   *Ответ:* Tag можно переназначить, digest однозначно фиксирует content.
