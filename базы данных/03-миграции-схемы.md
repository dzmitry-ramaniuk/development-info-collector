## Миграция как поставка

**Миграция схемы** — версионированное преобразование контракта хранения. Разделяйте schema migration, data migration/backfill, rollout приложения и поздний contract cleanup. Старые и новые экземпляры, jobs, BI и CDC могут использовать схему одновременно.

Миграции применяет один контролируемый job до запуска зависящего кода, а не каждый pod. Для этапов нужны владелец, метрики, abort criteria и runbook; тестовый объём должен быть production-подобным.

## Flyway и Liquibase

| Критерий | Flyway | Liquibase |
|---|---|---|
| Единица | SQL/Java migration | `changeSet` в changelog |
| История | Schema history и checksum | `DATABASECHANGELOG`, id/author/path, checksum |
| Сильная сторона | Прозрачный SQL, простая последовательность | Change types, contexts/labels, генерация SQL |
| Rollback | Часто compensating migration; возможности зависят от редакции | Явный/генерируемый rollback для поддерживаемых changes |

Пример Flyway:

```text
db/migration/
├── V001__create_booking_tables.sql
├── V002__add_booking_purpose.sql
└── R__booking_reporting_view.sql
```

Пример Liquibase formatted SQL:

```sql
--liquibase formatted sql
--changeset team:002 labels:booking
ALTER TABLE booking ADD COLUMN purpose text;
--rollback ALTER TABLE booking DROP COLUMN purpose;
```

> Строка rollback не делает откат безопасным: после записи в новую колонку её удаление теряет данные.

## Versioned и repeatable migrations

**Versioned migration** применяется один раз по порядку. Применённый файл неизменяем: исправление выпускают новой версией, иначе checksum обнаружит расхождение.

**Repeatable migration** без версии повторяется при изменении checksum. Она подходит для полностью пересоздаваемых view/functions, но не для неидемпотентного DML.

```sql
CREATE OR REPLACE VIEW booking_reporting AS
SELECT b.booking_id, b.room_id, b.starts_at,
       count(bp.user_id) AS participant_count
FROM booking AS b
LEFT JOIN booking_participant AS bp USING (booking_id)
GROUP BY b.booking_id;
```

В Liquibase `runOnChange` близок по назначению к repeatable; `runAlways` выполняется при каждом deployment и требует строгой идемпотентности.

## Backward compatibility и expand/contract

**Expand/contract** разносит несовместимое изменение:

1. **Expand:** добавить nullable-колонку/таблицу/индекс, не ломая старый код.
2. **Migrate:** dual-write, backfill истории, постепенное переключение чтения.
3. **Validate:** сверить данные и отдельно валидировать constraint.
4. **Contract:** после исчезновения старых клиентов прекратить старую запись и удалить объект.

Нельзя сразу переименовать `title` в `purpose`: старые instances потеряют колонку. Полезные защитные настройки PostgreSQL:

```sql
SET lock_timeout = '2s';
SET statement_timeout = '30s';
ALTER TABLE booking ADD COLUMN purpose text;
ALTER TABLE booking ADD CONSTRAINT booking_purpose_present
    CHECK (purpose IS NOT NULL) NOT VALID;
ALTER TABLE booking VALIDATE CONSTRAINT booking_purpose_present;
```

`NOT VALID` для поддерживаемого constraint откладывает проверку старых строк, но проверяет новые. Большой индекс обычно создают `CREATE INDEX CONCURRENTLY`; команда не допускается внутри transaction block, что учитывают в tool configuration. Lock level и длительность всегда проверяют на целевой версии и объёме.

## Backfill

Backfill должен быть идемпотентным, возобновляемым и ограниченным по нагрузке. Не объединяйте быстрый DDL и многомиллионный `UPDATE` в одну транзакцию.

```sql
WITH batch AS (
    SELECT booking_id FROM booking
    WHERE purpose IS NULL
    ORDER BY booking_id
    LIMIT 1000
    FOR UPDATE SKIP LOCKED
)
UPDATE booking AS b
SET purpose = b.title
FROM batch
WHERE b.booking_id = batch.booking_id AND b.purpose IS NULL
RETURNING b.booking_id;
```

Двигайтесь по стабильному ключу; управляйте batch/pause по latency, CPU, WAL и replication lag; измеряйте `NULL` и несовпадения. После первого прохода проверяйте конкурентный хвост. Определите источник истины и reconciliation.

## Rollback и roll-forward

Backward-compatible схема позволяет откатить **приложение**. Откат схемы после новых записей часто разрушителен, поэтому предпочтителен **roll-forward** или компенсирующая миграция.

| Ситуация | Действие |
|---|---|
| Nullable-колонка пока не нужна | Откатить приложение, колонку оставить |
| Ошибка во view/function | Исправить новой migration |
| Уже записан новый формат | Roll-forward с сохранением данных |
| Destructive DDL ещё не начат | Остановить rollout |

Для Liquibase сначала рецензируйте `update-sql`/`rollback-sql`: автоматический rollback доступен не всегда и не знает бизнес-семантики. Backup не заменяет совместимый план; восстановление проверяют с измеренными RTO/RPO.

## Сквозной пример

Заменим `booking.title` обязательным `purpose`.

1. **Релиз A:** `ALTER TABLE booking ADD COLUMN purpose text`; код читает `coalesce(purpose, title)` и пишет оба поля.
2. **Backfill:** worker выполняет batch выше; метрики показывают остаток и несовпадения.
3. **Релиз B:** чтение только `purpose`, dual-write пока сохраняется; `CHECK ... NOT VALID` добавлен и валидирован.
4. **Релиз C:** после rollback-window и инвентаризации consumers прекращается запись `title`, затем отдельная migration выполняет `ALTER TABLE booking DROP COLUMN title`.

Hibernate entity меняют по тем же фазам; автоматический destructive DDL не заменяет production migrations. См. [Hibernate/JPA](../java/04-hibernate.md).

## Чек-лист

- [ ] Старое и новое приложение проверены с expand-схемой.
- [ ] Известны блокировки, WAL и влияние на реплики.
- [ ] Заданы timeout, abort criteria и метрики.
- [ ] Backfill идемпотентен, возобновляем и наблюдаем.
- [ ] Применённые versioned migrations не редактируются.
- [ ] Generated SQL, checksum и права migration user проверены.
- [ ] Contract ждёт исчезновения старых приложений, jobs, BI и CDC.
- [ ] Есть roll-forward и проверенный restore.

## Упражнения

1. Превратите одношаговый `RENAME COLUMN` в expand/backfill/contract для rolling deployment.
2. Разбейте `NOT NULL` и `UPDATE` 200 млн строк на безопасные этапы и метрики остановки.
3. Разработчик изменил применённый `V002`: объясните checksum mismatch и выпустите `V003`, не скрывая проблему через `repair`.
4. Сделайте идемпотентным repeatable-файл с `INSERT`, создающим дубли.
5. Объясните потерю данных при `DROP COLUMN` после часа dual-write и предложите rollback приложения.
6. Спроектируйте замену статуса `cancelled` на `canceled` с учётом старых writers и CDC.

## Вопросы для самопроверки

1. **Почему deployment и миграция не атомарны?**
   *Ответ:* версии сосуществуют, DDL блокируется отдельно, backfill может длиться дольше rollout.
2. **Когда уместна repeatable migration?**
   *Ответ:* когда объект детерминированно пересоздаётся из полного определения, например view.
3. **Когда завершён backfill?**
   *Ответ:* после обработки истории и конкурентного хвоста, сверки и стабильных метрик dual-write.
