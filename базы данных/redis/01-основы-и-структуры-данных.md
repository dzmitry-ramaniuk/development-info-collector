## Модель Redis

**Redis** хранит ключи и типизированные значения преимущественно в памяти. Команды выполняются последовательно в основном event loop, поэтому отдельная команда атомарна, но долгий Lua-скрипт или команда над огромной коллекцией блокирует обработку других клиентов. Имена ключей проектируйте как контракт (`app:entity:id`), задавайте предел cardinality и lifecycle.

```redis
SET user:42:name "Анна" EX 3600 NX
TYPE user:42:name
TTL user:42:name
```

## Strings

**String** — байтовая последовательность до 512 MiB; подходит также для целых чисел и битовых операций.

```redis
SET session:7 '{"userId":42}' EX 1800
INCR rate:login:42
MGET feature:a feature:b
```

- **Подходит:** кэш сериализованного объекта, счётчик через `INCR`, idempotency key через `SET NX EX`, bitmap.
- **Не подходит:** частичное обновление большого JSON, неограниченный append, объект с часто меняющимися полями — перезапись и сериализация дают лишний трафик.

## Hashes

**Hash** группирует пары field-value под одним ключом.

```redis
HSET user:42 name "Анна" plan premium logins 1
HINCRBY user:42 logins 1
HMGET user:42 name plan
```

- **Подходит:** компактный профиль/агрегат, независимое атомарное изменение полей, счётчики сущности.
- **Не подходит:** запросы по значениям полей без отдельного индекса, огромный агрегат с разными TTL — expiry назначается ключу, а не отдельному field.

## Sets

**Set** — неупорядоченное множество уникальных строк.

```redis
SADD article:9:tags redis java cache
SISMEMBER article:9:tags redis
SINTER articles:read:42 articles:liked:42
```

- **Подходит:** уникальность, membership, теги, небольшие пересечения/объединения.
- **Не подходит:** упорядоченная выдача, хранение повторов, операции над гигантскими множествами в latency-sensitive контуре; используйте `SSCAN`, а не `SMEMBERS` без оценки размера.

## Sorted Sets

**Sorted Set** хранит уникальный member и числовой score, упорядочивая по score.

```redis
ZADD leaderboard 1200 user:42 1150 user:7
ZREVRANGE leaderboard 0 9 WITHSCORES
ZRANGEBYSCORE jobs -inf 1710000000
```

- **Подходит:** leaderboard, приоритетная очередь, временной индекс, sliding-window rate limit.
- **Не подходит:** строгая очередь с подтверждением обработки, сложная многополевая сортировка, бесконтрольная история без trimming.

## Streams

**Stream** — append-only журнал с ID, consumer groups, pending entries и явным подтверждением.

```redis
XADD orders MAXLEN ~ 100000 * orderId 123 status created
XGROUP CREATE orders billing 0 MKSTREAM
XREADGROUP GROUP billing worker-1 COUNT 10 BLOCK 2000 STREAMS orders >
XACK orders billing 1710000000000-0
```

- **Подходит:** ограниченный operational event log, work queue с consumer groups, replay в пределах retention.
- **Не подходит:** бесконечный durable log, cross-region event backbone, exactly-once. Обработчик обязан быть идемпотентным; контролируйте PEL, lag, trimming и reclaim зависших сообщений (`XAUTOCLAIM`).

## Pub/Sub

**Pub/Sub** доставляет сообщения только подписанным в данный момент клиентам и не хранит backlog.

```redis
SUBSCRIBE inventory.changed
PUBLISH inventory.changed '{"sku":"A-1"}'
```

- **Подходит:** transient notifications, live UI, локальная cache invalidation, когда потеря события допустима или компенсируется TTL/version check.
- **Не подходит:** финансовые события, offline consumers, retry/replay и гарантированная доставка. Для них выбирайте Streams или специализированный broker.

## Транзакции

`MULTI`/`EXEC` исполняет очередь команд без interleaving, но не даёт SQL rollback: runtime-ошибка одной команды не откатывает остальные. `WATCH` реализует optimistic locking; при изменении наблюдаемого ключа `EXEC` возвращает null и клиент повторяет операцию с ограниченным retry.

```redis
WATCH stock:sku-1
GET stock:sku-1
MULTI
DECR stock:sku-1
XADD stock-events * sku sku-1 delta -1
EXEC
```

- **Подходит:** атомарная группа заранее известных команд, compare-and-set с `WATCH`.
- **Не подходит:** длительная бизнес-транзакция, согласование Redis и SQL/Kafka, автоматический rollback. Для межсистемной согласованности применяйте outbox/saga и идемпотентность.

## Lua

Серверный Lua-скрипт атомарно выполняет несколько операций рядом с данными и сокращает round trips.

```lua
-- KEYS[1] — счётчик, ARGV[1] — TTL в секундах
local value = redis.call('INCR', KEYS[1])
if value == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return value
```

Запускайте через `EVALSHA`/Functions после загрузки, передавайте ключи через `KEYS`, а данные — через `ARGV`. В Cluster все затронутые ключи должны принадлежать одному hash slot (часто используют hash tag: `rate:{user42}:count`).

- **Подходит:** короткий bounded compare-and-update, rate limiter, условный delete lock token.
- **Не подходит:** CPU-heavy вычисления, I/O, неизвестное число элементов, долгие циклы. Скрипт блокирует event loop; задавайте клиентский deadline и наблюдайте latency.

## Практические рекомендации

- Избегайте `KEYS`, `SMEMBERS` и полного `HGETALL` на ключах неизвестного размера; используйте семейство `SCAN` и пагинацию.
- Оценивайте memory amplification командой `MEMORY USAGE`, а не только размер payload.
- Не помещайте секреты в имена ключей: имена видимы в диагностике и telemetry.
- Для каждой структуры задайте максимальный размер, retention, TTL, owner и способ восстановления.

## Вопросы для самопроверки

1. **Чем Streams отличаются от Pub/Sub?** Streams сохраняют записи, поддерживают replay, consumer groups и acknowledgment; Pub/Sub доставляет только онлайн-подписчикам.
2. **Даёт ли `MULTI` rollback?** Нет; он гарантирует последовательное выполнение очереди, но не откатывает уже выполненные команды из-за runtime-ошибки.
3. **Почему Lua должен быть коротким?** Скрипт атомарен и на время выполнения блокирует обработку остальных команд.
4. **Когда Hash хуже String?** Когда объект читается/пишется целиком, нужна единая сериализованная схема или отдельные поля требуют разных TTL.
