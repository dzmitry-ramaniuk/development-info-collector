## Границы применения

Redis особенно полезен как быстрый кэш, ephemeral state, rate limiter, leaderboard и транспорт для ограниченных потоковых сценариев. Он не заменяет автоматически долговечную транзакционную БД: модель согласованности, объём памяти, потеря подтверждённых записей при failover и семантика доставки должны соответствовать требованиям системы.

> Сначала сформулируйте допустимую потерю данных (RPO), время восстановления (RTO), семантику доставки и бюджет памяти; только затем выбирайте standalone, Sentinel или Cluster.

## Практический маршрут

1. Запустите Redis 8.2.x локально и попробуйте команды каждого типа данных.
2. Реализуйте cache-aside с TTL, jitter и negative caching.
3. Смоделируйте остановку primary и проверьте фактические RPO/RTO.
4. Напишите Java-тест с Testcontainers, проверяющий сериализацию, expiry и поведение при timeout.
