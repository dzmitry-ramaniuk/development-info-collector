## RDB и AOF

**RDB** создаёт point-in-time snapshot. Плюсы: компактность, быстрый restart/backup; минусы: между snapshot возможна потеря минут данных, fork и copy-on-write требуют памяти и I/O.

**AOF** журналирует изменения и поддерживает `appendfsync always|everysec|no`. Типичный `everysec` балансирует latency и RPO порядка секунды, но это не абсолютная гарантия при сбоях ОС/диска. Rewrite компактизирует журнал и тоже создаёт I/O/COW pressure.

| Режим | Подходящий сценарий | Неподходящий сценарий |
|---|---|---|
| Без persistence | Восстанавливаемый кэш | Redis — единственная копия состояния |
| RDB | Backup, быстрый restore, допустим широкий RPO | Почти нулевая потеря записей |
| AOF `everysec` | Малый RPO при приемлемой цене | Требование подтверждать только fsync каждой записи |
| RDB + AOF | Более сильная recoverability | Окружение без I/O/RAM budget и проверок restore |

При включённых RDB+AOF Redis при restart восстанавливается из AOF. Persistence — не backup: репликация и ошибочное `DEL` распространяют повреждение. Храните off-host версии, проверяйте checksum и регулярно выполняйте restore drill.

## Replication

Репликация primary→replica асинхронна. Replica помогает reads и failover, но stale reads и потеря подтверждённых primary записей возможны. `WAIT` ждёт подтверждения репликами и уменьшает вероятность потери, однако не превращает Redis в CP-систему и не гарантирует disk fsync.

Full sync передаёт snapshot; partial resynchronization использует replication backlog и offsets. Недостаточный backlog или долгая сеть вызывают дорогой full resync. Не направляйте чтения на replicas, если read-after-write обязателен без дополнительной координации.

## Sentinel

**Sentinel** наблюдает standalone primary/replicas, достигает quorum по недоступности, выбирает replica и сообщает клиентам новый primary. Разворачивайте минимум три Sentinel в независимых failure domains; Sentinel не шардирует данные.

Failover остаётся асинхронным: возможны потеря последних writes, split-brain clients и кратковременная недоступность. Клиент должен поддерживать Sentinel discovery, reconnect, bounded retry и не повторять неидемпотентную операцию вслепую после ambiguous timeout.

- **Подходит:** один dataset помещается на узел, нужны replicas и автоматический failover.
- **Не подходит:** горизонтальное распределение dataset/throughput — нужен Cluster или иной sharding.

## Cluster

**Redis Cluster** делит keyspace на 16 384 hash slots. Каждый primary владеет диапазоном slots; replicas обеспечивают failover. Клиент обязан понимать `MOVED`/`ASK` и topology refresh. Multi-key операция, транзакция или Lua возможны только для ключей одного slot; hash tags (`order:{42}:state`, `order:{42}:items`) колоцируют связанные ключи.

- **Подходит:** dataset или write throughput превышает один узел, приемлема slot-based модель.
- **Не подходит:** произвольные cross-key joins/transactions, строгая доступность minority partition, «один огромный hot key» — шардирование его не распределит.

Миграцию slots, rebalancing и failover тестируйте под реальной нагрузкой. Не складывайте все ключи под один hash tag: это отменяет шардирование.

## Hot keys и big keys

**Hot key** концентрирует CPU/network на одном owner; реплики или client-side local cache помогают только read workload. Разбивайте счётчики на shards с последующей агрегацией, реплицируйте immutable reads, применяйте request coalescing и rate limiting. Измеряйте распределение, а не только среднюю нагрузку.

**Big key** увеличивает latency удаления/сериализации, блокирует event loop командами O(N) и усложняет migration. Ищите через `redis-cli --bigkeys`/`--memkeys`, sampling `SCAN` + `MEMORY USAGE`, latency diagnostics. Удаляйте асинхронно `UNLINK`, дробите данные, ограничивайте `MAXLEN`, избегайте полного чтения коллекции.

## Memory fragmentation

Сравнивайте `used_memory`, `used_memory_rss`, `mem_fragmentation_ratio` и абсолютную разницу RSS-used; один ratio при малом dataset вводит в заблуждение. Причины: allocator size classes, churn разного размера, fork/COW, невозможность ОС сразу вернуть страницы.

Действия: подтвердить тренд и headroom, устранить churn/big keys, рассмотреть `activedefrag` после нагрузочного теста, планово перезапустить replica и выполнить failover, если память нельзя вернуть безопасно. Никогда не рестартуйте primary вслепую ради «красивого ratio».

## Observability

Минимальный dashboard и alerts:

- **Нагрузка:** ops/sec, command latency p50/p95/p99, slow log, blocked clients, rejected connections.
- **Кэш:** hits/misses и hit ratio по приложению, evictions, expirations, fill latency/error, stampede concurrency.
- **Память:** used/max/RSS, fragmentation, key count, big/hot keys, fork/COW peak.
- **Persistence:** last save/AOF status, fsync latency, rewrite duration/error, disk space.
- **Replication:** role, link status, offset/lag, backlog, full sync count.
- **Sentinel/Cluster:** quorum, failover events, unhealthy slots, `cluster_state`, slot coverage, redirects.
- **Хост:** CPU (включая steal), network saturation/retransmits, disk latency, file descriptors.

`MONITOR` дорог и раскрывает данные — только кратко в контролируемом окружении. Slow log показывает server execution, но не DNS/pool/network; объединяйте Redis metrics с client-side latency и traces. Не включайте raw values/PII в логи.

## Потеря узла

### До инцидента

1. Зафиксировать RPO/RTO, topology, владельца и runbook.
2. Проверять backups restore-тестом; мониторить replica lag и disk.
3. Провести game day: kill primary, network partition, disk full, потеря AZ.
4. Убедиться, что клиенты обновляют topology/Sentinel адрес и retries bounded.

### Во время инцидента

1. Объявить инцидент; сохранить timeline и не запускать одновременно несколько failover.
2. Определить роль узла, scope, quorum/slot coverage и состояние surviving replicas.
3. **Sentinel:** подтвердить автоматический promotion; при ручном failover выбрать наиболее свежую replica и оценить data loss.
4. **Cluster:** проверить `CLUSTER INFO`/`CLUSTER NODES`, coverage slots; promote replica штатным механизмом, не назначать slots пустому узлу без решения о потере данных.
5. Переключить/проверить клиентов, ограничить нагрузку и отключить опасные retries; для кэша защищать source DB от cold-start storm.
6. Сравнить replication offsets/AOF/RDB и не возвращать старый primary как writable до rejoin/resync.

### После восстановления

Восстановить redundancy, проверить целостность на уровне бизнеса и обработать ambiguous writes идемпотентно. Постепенно прогреть кэш, наблюдать p99/DB load, затем провести postmortem и restore/failover drill с исправленным runbook.

## Практический чек-лист

- [ ] `maxmemory`, policy и headroom заданы явно.
- [ ] Persistence соответствует RPO; backup восстановлен на отдельном стенде.
- [ ] Replica lag, AOF/RDB errors, evictions и slot coverage имеют alerts.
- [ ] Клиентские connect/command timeouts и retry budget проверены fault injection.
- [ ] Runbook различает cache loss и authoritative state loss.

## Вопросы для самопроверки

1. **Почему replica не является backup?** Ошибки и удаления реплицируются, а failover не хранит независимую историю.
2. **Что теряется при Sentinel failover?** Возможны последние writes, ещё не дошедшие до promoted replica.
3. **Почему Cluster не исправляет hot key?** Один key принадлежит одному slot и обслуживается одним primary.
4. **Что делать первым при потере primary?** Установить scope/роль и состояние quorum/replicas; не выполнять конфликтующие ручные действия до оценки.
