## Актуальность материала

- **Дата проверки:** 4 августа 2026 года.
- **Целевая база:** стабильная реляционная теория; DDL проверен для PostgreSQL 18.
- **Статус примеров:** `current`.
- **Первичные источники:** [PostgreSQL 18: Constraints](https://www.postgresql.org/docs/18/ddl-constraints.html), [PostgreSQL 18: CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html), [ISO/IEC 9075-2:2023](https://www.iso.org/standard/76584.html).

**Отношение** — множество кортежей одинаковой структуры. Таблица SQL приближает эту модель, но допускает `NULL` и дубли без ключа. Проектирование начинают с сущностей, жизненных циклов, кардинальностей и инвариантов, а не со списка колонок.

## Ключи и ограничения

| Понятие | Смысл | Пример |
|---|---|---|
| Суперключ | Набор атрибутов, однозначно определяющий строку | `(room_id, name)` при уникальном `room_id` |
| Кандидатный ключ | Минимальный суперключ | `room_id`, `room_code` |
| Первичный ключ | Выбранный кандидатный ключ | `room_id PRIMARY KEY` |
| Альтернативный ключ | Остальной кандидат | `room_code UNIQUE NOT NULL` |
| Внешний ключ | Ссылочная целостность | `booking.room_id` → `room.room_id` |

`PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `NOT NULL` и `CHECK` делают недопустимые состояния непредставимыми. `CHECK` в PostgreSQL не предназначен для правил между строками: используйте ключ, exclusion constraint, триггер или измените модель. `ON DELETE CASCADE` подходит зависимым объектам без своего жизненного цикла; для аудита обычно безопаснее `RESTRICT`.

## Функциональные зависимости и нормальные формы

**Функциональная зависимость** `X → Y` означает: одинаковые `X` всегда дают одинаковые `Y`. Это правило предметной области, а не случайное свойство тестовых данных. Если `booking_id → room_id, starts_at, organizer_id`, то `booking_id` — суперключ.

| Форма | Требование | Устраняемый дефект |
|---|---|---|
| 1NF | Одно значение домена в ячейке, нет повторяющихся групп | CSV и `participant_1`, `participant_2` |
| 2NF | 1NF и нет зависимости неключевого атрибута от части составного ключа | `user_name` в связи с ключом `(booking_id, user_id)` |
| 3NF | 2NF и нет транзитивной зависимости неключевых атрибутов от ключа | `room_id → building_id → address` |
| BCNF | В любой нетривиальной `X → Y` детерминант `X` — суперключ | Остаточные аномалии 3NF при пересекающихся кандидатных ключах |

BCNF строже 3NF. Декомпозиция должна быть **без потерь** (`lossless join`) и желательно сохранять зависимости. Нормализация — не механическое дробление: сначала фиксируют зависимости, затем проверяют доказуемые свойства результата.

## Моделирование связей

- **1:1:** FK с `UNIQUE`; часто достаточно общей таблицы.
- **1:N:** FK на стороне N, например `booking.room_id`.
- **M:N:** таблица связи с двумя FK и обычно составным PK; её атрибуты описывают связь.
- **Иерархия:** adjacency list (`parent_id`) прост, обход выполняется рекурсивным CTE.

Nullable FK допустим, только если отсутствие связи имеет предметный смысл. Массив идентификаторов или JSON не заменяет таблицу связи, когда нужны FK, уникальность пары и атрибуты связи.

## Сквозной пример

Небольшой сервис хранит комнаты, пользователей, брони и участников:

```sql
CREATE TABLE app_user (
    user_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE,
    display_name text NOT NULL CHECK (display_name <> '')
);

CREATE TABLE room (
    room_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_code text NOT NULL UNIQUE,
    name text NOT NULL,
    capacity integer NOT NULL CHECK (capacity > 0)
);

CREATE TABLE booking (
    booking_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id bigint NOT NULL REFERENCES room(room_id) ON DELETE RESTRICT,
    organizer_id bigint NOT NULL REFERENCES app_user(user_id) ON DELETE RESTRICT,
    title text NOT NULL,
    starts_at timestamptz NOT NULL,
    ends_at timestamptz NOT NULL,
    status text NOT NULL CHECK (status IN ('planned', 'cancelled')),
    CHECK (ends_at > starts_at)
);

CREATE TABLE booking_participant (
    booking_id bigint NOT NULL REFERENCES booking(booking_id) ON DELETE CASCADE,
    user_id bigint NOT NULL REFERENCES app_user(user_id) ON DELETE RESTRICT,
    response text NOT NULL DEFAULT 'pending'
        CHECK (response IN ('pending', 'accepted', 'declined')),
    PRIMARY KEY (booking_id, user_id)
);
```

Адрес комнаты не копируется в бронь, а M:N вынесена в `booking_participant`. DDL ещё не запрещает пересечения времени одной комнаты: это межстрочное правило. В PostgreSQL подходит exclusion constraint с range-типом; переносимый вариант требует корректной конкурентной транзакции. См. [транзакции PostgreSQL](postgresql/05-transactions.html) и [маппинг связей Hibernate](../java/04-hibernate.html).

## Денормализация

**Денормализация** — осознанное хранение производных/дублированных данных ради измеримой цели. Например, `participant_count` ускоряет список, но создаёт второй источник состояния.

Перед ней измеряют запрос и план, определяют источник истины и допустимую задержку, выбирают атомарное или асинхронное обновление, добавляют сверку и восстановление. Отличайте исторический снимок (имя на момент брони) от кеша. ORM и JSON не отменяют функциональные зависимости.

5. Предложите контролируемую денормализацию числа будущих броней и способ обнаружить рассинхронизацию.

## Вопросы для самопроверки

1. **Кандидатный ключ и `PRIMARY KEY` — одно и то же?**
   *Ответ:* кандидатов может быть несколько; первичным назначают один, остальные защищают `UNIQUE NOT NULL`.
2. **Почему 3NF не всегда BCNF?**
   *Ответ:* 3NF допускает зависимость от не-суперключа, если зависимый атрибут входит в кандидатный ключ; BCNF — нет.
3. **Нормализация гарантирует скорость?**
   *Ответ:* нет, она уменьшает аномалии. Производительность измеряют и только затем контролируемо денормализуют.
