## Как работать с разделом

Практикумы — это открытые архитектурные задачи: исходные числа являются гипотезами, а не скрытым ответом. На каждом этапе зафиксируйте assumptions, ADR, измеримые SLO, бюджет ошибок и причины выбора. Затем проведите архитектурное ревью, сравнив минимум два варианта.

**Базовый результат** — реализованный первый этап и воспроизводимые сценарии корректности. **Production-профиль** — этапы эксплуатации и нагрузки с измерениями. **Advanced-профиль** — миграции и региональный DR. Начинающему не требуется сразу разворачивать multi-region; проектное описание без выполнения эксперимента помечайте как гипотезу, а не как подтверждённую гарантию.

Перед стартом полезно повторить [Java](../java/README.html), [PostgreSQL](../базы%20данных/postgresql/README.html), [Kafka](../очереди/кафка/README.html), [тестирование](../тестирование/README.html), [Kubernetes](../kubernetes/README.html), [AWS](../aws/README.html) и [System Design](../system%20design/README.html).

## Рекомендуемые траектории

- **Backend с нуля:** Java/Spring → PostgreSQL → тестирование → кейс 1 → Kafka → кейс 2 → Kubernetes → кейс 3.
- **System Design interview:** основы и оценка нагрузки → для каждого кейса выполнить этапы без подсказок → защитить trade-offs и план capacity/DR.
- **Production engineering:** observability и security → Kubernetes/AWS → этапы эксплуатации и отказов во всех трёх кейсах.
- **Event-driven:** Kafka → кейс 2 → асинхронные части кейса 3 → сравнение outbox, CDC и dual write.

## Общий формат результата

1. Контекст и словарь, assumptions и расчёты с единицами измерения.
2. API/event schemas, модель данных и диаграммы контекста/контейнеров.
3. ADR с альтернативами, стоимостью обратимости и критериями пересмотра.
4. План тестов, SLI/SLO, алерты, runbook, capacity forecast и DR drill.
5. Список открытых вопросов: допустимы разные решения, если они проверяемы и согласованы с требованиями.

Для каждого сценария приёмки сохраните: версии приложения/окружения, seed или fixture, команду запуска, workload с длительностью, точку инъекции отказа, ожидаемый инвариант, фактическое число эффектов и метрики. Секреты и пользовательские данные в доказательства не включайте. Реализация может использовать собственный harness; описание «тест прошёл» без входов и наблюдаемого результата не воспроизводится.

Оцените каждую область — **корректность**, **достижимость SLO**, **отказы/восстановление**, **альтернативы и стоимость** — по шкале: 0 = только заявление; 1 = связная модель и план проверки; 2 = приложено воспроизводимое доказательство. Обязательные инварианты этапа должны быть доказаны независимо от суммы баллов. Для выбора следующей темы используйте область с минимальной оценкой.
