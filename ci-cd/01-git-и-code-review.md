## Актуальность материала

- **Проверено:** 4 августа 2026 года.
- **Целевые спецификации:** Git 2.x; Conventional Commits 1.0.0; Semantic Versioning 2.0.0.
- **Статус примеров:** `current`; модели ветвления — концептуальны, настройки защиты веток зависят от платформы.
- **Первичные источники:** [Git branching workflows](https://git-scm.com/book/en/v2/Git-Branching-Branching-Workflows), [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/), [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html), [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## Цель процесса

Git workflow оптимизируют не ради «красивого графа», а ради короткого и проверяемого пути изменения в production. Хороший процесс уменьшает batch size, время обратной связи и число конфликтов, сохраняя трассируемость решения.

> Ветка не является средой, а merge не является deployment. Коммит идентифицирует исходный код; release должен дополнительно идентифицировать собранный артефакт.

## Trunk-based development и GitFlow

**Trunk-based development (TBD)** предполагает частую интеграцию в одну основную ветку. Короткоживущая feature-ветка допустима, если живёт часы или несколько дней, регулярно синхронизируется и быстро сливается. Незавершённое поведение скрывают feature flag или branch by abstraction.

**GitFlow** использует долгоживущие `main` и `develop`, feature-, release- и hotfix-ветки. Он делает параллельную стабилизацию релиза явной, но увеличивает число merge, время до интеграции и риск расхождения веток.

| Критерий | Trunk-based development | GitFlow |
|---|---|---|
| Частота интеграции | Несколько раз в день | После завершения feature/release |
| Цена | Требует быстрый CI, flags и дисциплину | Требует управления ветками и обратными merge |
| Подходит | Continuous delivery, единая развиваемая версия | Несколько поддерживаемых версий, релизные окна |
| Главный риск | Сломать trunk без надёжных gates | Большие конфликты и поздняя обратная связь |

Выбор не бинарный: продукт может работать trunk-based, а поддерживаемые версии получать короткие release branches. Не копируйте GitFlow только потому, что релизы редки: сначала выясните, действительно ли параллельно поддерживаются разные линии кода.

## Маленькие pull request

**Маленький pull request (PR)** должен выражать одну цель и быть независимо проверяемым. Размер не равен фиксированному числу строк: generated code и механическое переименование отличаются от изменения бизнес-логики. Практические признаки:

- описание объясняет проблему, решение, риск, тесты и способ rollback;
- рефакторинг отделён от изменения поведения;
- schema/API changes совместимы с предыдущей версией;
- PR можно качественно просмотреть за один подход;
- screenshots, логи или результаты нагрузочных проверок приложены только когда релевантны.

Большую функцию дробят вертикально: совместимый API/схема → скрытая реализация → включение flag → удаление старого пути. «Draft PR на 5 000 строк» не становится маленьким из-за раннего открытия.

## Review и обязательные проверки

Code review проверяет корректность замысла и эксплуатационные последствия, а автоматизация — повторяемые свойства. Reviewer проверяет:

1. соответствие acceptance criteria и архитектурным ограничениям;
2. безопасность, обработку ошибок, совместимость и миграцию данных;
3. достаточность тестов и наблюдаемость;
4. rollout/rollback и документацию.

Branch protection/ruleset обычно запрещает прямой push и требует:

- один или несколько approvals, включая CODEOWNERS для критичных областей;
- успешные именованные status checks и актуальность ветки относительно trunk;
- разрешённую стратегию merge и проверенные/подписанные коммиты при необходимости;
- снятие старых approvals после изменения кода;
- отдельный, аудируемый break-glass для инцидента.

Не делайте все проверки блокирующими: быстрые deterministic checks — gate PR; долгие performance/chaos-тесты могут идти по расписанию, но release policy обязана указать, когда они становятся gate.

## Conventional Commits и Semantic Versioning

Conventional Commits задаёт структуру сообщения:

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footer]
```

```text
feat(checkout): добавить расчёт скидки
fix(api): не возвращать секрет в ответе
feat(auth)!: удалить устаревший token endpoint

BREAKING CHANGE: клиенты должны использовать /oauth/token
```

- `fix` обычно соответствует PATCH, `feat` — MINOR;
- `!` или footer `BREAKING CHANGE:` сигнализирует MAJOR;
- `docs`, `test`, `refactor`, `build`, `ci`, `chore` — полезные соглашения команды, но спецификация не диктует их влияние на версию.

**Semantic Versioning (SemVer)** имеет форму `MAJOR.MINOR.PATCH`: MAJOR — несовместимое публичное API, MINOR — обратно совместимая функциональность, PATCH — обратно совместимое исправление. Pre-release (`1.4.0-rc.1`) имеет меньший precedence, build metadata (`+build.42`) precedence не меняет.

> Автоматический release по типам коммитов корректен лишь при определённом публичном API и качественной проверке breaking changes. Squash merge требует сформировать Conventional Commit в заголовке итогового commit.

## Практический пример

```bash
git switch -c feat/order-timeout
git add src test
git commit -m "feat(order): добавить настраиваемый timeout"
git fetch origin
git rebase origin/main
git push -u origin feat/order-timeout
```

Чек-лист PR:

- [ ] Изменение мало и имеет одну цель.
- [ ] Тесты доказывают новое поведение и важные ошибки.
- [ ] Миграция обратно совместима; секретов и generated artifacts в Git нет.
- [ ] Описаны метрики, rollout, feature flag и rollback, если риск этого требует.
- [ ] Итоговый commit соответствует принятому формату.

## Типичные ошибки

- **Долгоживущие ветки:** интегрировать чаще и скрывать незавершённое flags.
- **Approval как формальность:** назначать владельца риска, ограничивать размер PR и автоматизировать рутину.
- **Администратор всегда обходит gates:** использовать временный break-glass с причиной и последующим аудитом.
- **Версия вычисляется по каждому commit в PR:** вычислять по commit, который действительно попал в защищённую ветку.
- **Breaking change спрятан в `fix`:** анализировать контракт, а не только префикс сообщения.

## Практические упражнения

1. Спроектируйте ruleset для `main`: проверки, approvals, CODEOWNERS и emergency path.
2. Разделите крупную замену API на четыре обратно совместимых PR.
3. Определите версии после `fix`, `feat` и `BREAKING CHANGE` для релиза `2.3.4`.

## Вопросы для самопроверки

1. **Почему TBD требует feature flags?** Чтобы интегрировать неполную реализацию без открытия её всем пользователям.
2. **Когда GitFlow оправдан?** Когда действительно нужны параллельная стабилизация и поддержка нескольких релизных линий.
3. **Заменяют ли обязательные checks review?** Нет: они проверяют формализованные свойства, а reviewer — смысл, риск и полноту решения.
4. **Всегда ли `feat` означает MINOR?** Только в рамках согласованного публичного API и release policy.
