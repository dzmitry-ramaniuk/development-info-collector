## Модель данных и strong consistency

**Amazon S3** — объектное хранилище. С декабря 2020 года S3 предоставляет **strong read-after-write consistency** для `PUT`, overwrite, `DELETE`, чтения объекта, metadata/tags/ACL и `LIST` во всех регионах: успешная запись немедленно видна последующему чтению и listing. Это не транзакция между несколькими ключами и не взаимное исключение конкурентных writers: для optimistic concurrency применяйте `ETag` и conditional requests (`If-Match`/`If-None-Match`). Подтверждение модели — в [S3 data consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).

## Block Public Access и политики

**S3 Block Public Access (BPA)** — защитный слой на уровнях организации, аккаунта, bucket и access point. Четыре настройки блокируют новые public ACL, игнорируют любые public ACL, блокируют новые public bucket/access-point policies и ограничивают доступ через уже public policies. S3 применяет наиболее строгую комбинацию. Для новых buckets BPA включён по умолчанию, но production baseline — явно закрепить его через IaC и AWS Organizations; BPA не заменяет least-privilege IAM/bucket policy.

Публичную раздачу обычно организуют через CloudFront Origin Access Control и закрытый bucket. Для временной загрузки или скачивания используйте короткоживущие pre-signed URLs и ограничивайте content type/size на уровне приложения.

## Object Ownership

Режим **Bucket owner enforced** для S3 Object Ownership отключает ACL и гарантирует владение bucket owner всеми объектами; для новых buckets он включён по умолчанию. Управляйте доступом через IAM, bucket/access-point policies. Это устраняет типичную проблему cross-account uploads, когда объект принадлежал writer. ACL включайте только ради подтверждённой legacy-интеграции.

## Versioning и восстановление

- **Versioning** сохраняет разные версии одного key и защищает от случайного overwrite/delete; обычный `DELETE` создаёт delete marker, но удаление конкретного `versionId` окончательно.
- После включения versioning можно приостановить, но нельзя вернуть bucket в never-versioned состояние.
- Versioning не является независимым backup: настройте least privilege, Object Lock/MFA Delete при необходимости и cross-account/region replication по RPO/RTO.
- Контролируйте стоимость noncurrent versions и incomplete multipart uploads через lifecycle.

## Lifecycle и стоимость

**Lifecycle configuration** выполняет переходы между storage classes и expiration текущих версий, noncurrent versions, delete markers и незавершённых multipart uploads. Правила асинхронны: объект может исчезнуть не точно в момент достижения возраста. Учитывайте minimum storage duration, minimum billable object size, retrieval fees и ограничения переходов; сверяйте их с [S3 pricing](https://aws.amazon.com/s3/pricing/).

Пример baseline-правила для versioned log bucket:

```json
{
  "Rules": [{
    "ID": "archive-and-cleanup",
    "Status": "Enabled",
    "Filter": {"Prefix": "logs/"},
    "Transitions": [{"Days": 30, "StorageClass": "STANDARD_IA"}],
    "NoncurrentVersionExpiration": {"NoncurrentDays": 90},
    "AbortIncompleteMultipartUpload": {"DaysAfterInitiation": 7}
  }]
}
```

Числа в примере — архитектурная политика, а не AWS quota. На 4 августа 2026 года service quotas, доступные storage classes и экономическая выгода зависят от региона, размера и access pattern; проверяйте [S3 quotas](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ServiceQuotas.html) и Storage Class Analysis.

## Практический baseline для production

1. `BucketOwnerEnforced`, BPA на всех уровнях и запрет небезопасного transport.
2. Versioning, encryption и recovery test; Object Lock только с понятной retention governance.
3. Lifecycle отдельно для current/noncurrent versions, delete markers и multipart uploads.
4. CloudTrail data events/S3 Inventory/Storage Lens по требованиям наблюдаемости и стоимости.
5. Conditional writes при конкурирующих writers; не проектируйте multi-object transaction поверх S3.
