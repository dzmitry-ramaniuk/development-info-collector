## Актуальность материала

- **Дата проверки:** 2026-10-15 — точечная сверка поверхностной неизменяемости record и двух новых упражнений; обзор архитектурных подходов не является полной ревизией каждого паттерна.
- **Целевая версия или диапазон:** Java SE 17–21.
- **Статус примеров:** `current`; оба упражнения проверены в CoreExamples с --release 17 на JDK 21.0.12.1.
- **Первичные источники:** [Record API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Record.html); [JLS Interfaces](https://docs.oracle.com/javase/specs/jls/se21/html/jls-9.html).

## Принципы проектирования
- **Инкапсуляция** — скрывайте внутреннее состояние за методами доступа. Используйте `private` поля и иммутабельные объекты,
  где это возможно.
- **Наследование** — применяйте для моделирования отношения «is-a». Не злоупотребляйте глубокой иерархией; если требуется
  совместное поведение, подумайте о композиции.
- **Полиморфизм** — интерфейсы и абстрактные классы позволяют подменять реализации и строить расширяемые API.
- **SOLID** — Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. В Java
  эти принципы реализуются через интерфейсы, фабрики, DI-фреймворки.

## Проектирование классов и API
1. **Иммутабельность**: делайте классы неизменяемыми, когда это возможно. Для value-объектов полезен `record`, но его поля только поверхностно неизменяемы: mutable-компоненты нужно копировать. `Builder` упрощает создание объекта и сам по себе не гарантирует неизменяемость.
2. **Контракты equals/hashCode**: переопределяйте в паре. Соблюдайте рефлексивность, симметричность, транзитивность.
3. **Comparable и Comparator**: реализуйте естественный порядок (`Comparable`) и внешние сравнения (`Comparator.comparing`).
4. **Фабрики и конструкторы**: статические фабрики (`of`, `from`, `valueOf`) удобнее, когда нужно кэшировать экземпляры.
5. **Документация**: описывайте ограничения, побочные эффекты и потокобезопасность через Javadoc и аннотации (`@ThreadSafe`).

## Паттерны проектирования
- **Creational**: Singleton (с Enum), Builder, Factory Method, Abstract Factory.
- **Structural**: Adapter, Decorator, Facade, Proxy.
- **Behavioral**: Strategy, Template Method, Observer, Command.

Практика: анализируйте стандартную библиотеку (например, `java.nio.file.Files` как фасад, `Collections.unmodifiableList` как
декоратор) и заимствуйте подходы.

## Работа с интерфейсами и абстракциями
С Java 8 интерфейсы поддерживают `default`-методы, что облегчает эволюцию API. Используйте `sealed` интерфейсы для ограниченных
иерархий, `static` методы для фабрик, `private` методы для реюза логики. Абстрактные классы храните для общих состояний и
защищённых хелперов.

## Архитектурные подходы
- **Domain-Driven Design** — агрегаты, value-объекты, репозитории.
- **Hexagonal Architecture** — разделение домена и адаптеров (портов).
- **Event-driven** — события как интерфейсы, обработчики как реализации.

Выбирайте архитектурный стиль исходя из требований проекта: DDD подходит для сложного домена, а модульные монолиты — для
приложений с единым деплоем, но разными bounded contexts.

## Практические упражнения

### Упражнение 1: неизменяемый список треков

**Задание:** создайте `Playlist(List<String> tracks)`. После создания изменение исходного списка не должно менять плейлист;
через accessor также нельзя добавить трек. Для простоты элементы — неизменяемые строки, `null` запрещён.

**Вход:** список `["A"]`; после создания плейлиста добавьте в исходный список `"B"`.
**Ожидается:** плейлист по-прежнему содержит `["A"]`, а `playlist.tracks().add("C")` бросает `UnsupportedOperationException`.

**Решение:**

```java
import java.util.ArrayList;
import java.util.List;

record Playlist(List<String> tracks) {
    Playlist {
        tracks = List.copyOf(tracks);
    }
}

// Внутри main:
List<String> source = new ArrayList<>(List.of("A"));
Playlist playlist = new Playlist(source);
source.add("B");
System.out.println(playlist.tracks()); // [A]
```

`final` запрещает заменить поле, но не изменить объект по ссылке. Копия разрывает связь с исходным списком и запрещает
изменение самого списка. Если элементы mutable, нужно отдельно решить, как копировать и защищать их состояние.
Это различие описано в [контракте Record](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Record.html).

**Критерий решения:** обе проверки проходят; читатель объясняет, почему пустой `record Playlist(List<String> tracks) {}` их не проходит.

### Упражнение 2: композиция и Strategy для расчёта цены

**Задание:** обычный заказ и заказ со скидкой должны использовать одинаковый расчёт с подставляемой политикой.
Суммы выражены целым числом минимальных денежных единиц. Политика не может вернуть отрицательную цену или увеличить её.

**Вход:** сумма `200`, обычная политика и скидка 10 % с целочисленным округлением вниз суммы скидки.
**Ожидается:** `200` и `180`; политика `value -> -1` отклоняется.

**Решение:**

```java
import java.util.function.LongUnaryOperator;

static long price(long subtotal, LongUnaryOperator discount) {
    if (subtotal < 0) throw new IllegalArgumentException("negative subtotal");
    long result = discount.applyAsLong(subtotal);
    if (result < 0 || result > subtotal) {
        throw new IllegalArgumentException("discount outside [0, subtotal]");
    }
    return result;
}

// Внутри main:
System.out.println(price(200, value -> value));              // 200
System.out.println(price(200, value -> value - value / 10)); // 180
```

Это фрагмент методов класса; полная программа находится в [CoreExamples.java](../../examples/java-core/CoreExamples.java).
Композиция позволяет добавить политику без подкласса `Order` с неожиданно изменённым контрактом. Контракт операции задаёт
допустимые результаты всех реализаций: добавление проверки только в одном подклассе не исправляет нарушение LSP.

**Критерий решения:** две политики дают ожидаемый результат; неправильная политика отклоняется; добавление третьей не требует изменения `price`.

## Вопросы на собеседовании
1. **Когда лучше использовать композицию вместо наследования?**
   *Ответ:* Когда требуется повторное использование поведения без жёсткой иерархии. Композиция позволяет подменять компоненты,
   облегчает тестирование и снижает связанность.
2. **Как гарантировать неизменяемость класса?**
   *Ответ:* Сделать поля `private final`, не предоставлять сеттеры, копировать изменяемые аргументы и коллекции, объявить класс
   `final`. У `record` final-поля генерируются автоматически, но изменяемые компоненты требуют защитных копий; для списка неизменяемых строк достаточно `List.copyOf`.
3. **В чём отличие интерфейса от абстрактного класса?**
   *Ответ:* Интерфейсы не содержат изменяемого состояния экземпляра: их поля — `public static final`. `default` и `static` методы задают поведение, а не хранимое состояние. Интерфейсы поддерживают множественное наследование типов. Абстрактные классы могут хранить состояние, предоставлять частичную реализацию, но наследуются только от одного
   базового класса.
4. **Как реализовать корректный паттерн Singleton?**
   *Ответ:* Использовать `enum Singleton { INSTANCE; }` или `private static class Holder`. Такие реализации потокобезопасны и
   обеспечивают безопасную ленивую инициализацию. Enum также сохраняет singleton-семантику при стандартной сериализации; Holder сам по себе её не обеспечивает — сериализуемому классу может понадобиться `readResolve`.
5. **Что такое Liskov Substitution Principle и как его нарушить?**
   *Ответ:* Принцип требует, чтобы подкласс можно было использовать вместо базового класса без изменения корректности. Нарушение
   возникает, если подкласс ужесточает предусловия или ослабляет постусловия (например, метод `Square` переопределяет `setWidth`
   и ломает поведение базового `Rectangle`).
